# gspot.toml: the settings file and its code

`gspot.toml` is the one file a user edits. It holds the level, the chosen configurations, every setting, every
accepted finding, and the repository's own command checks. The code that reads, checks, and writes it lives in
`packages/cli/src/policy/` today and becomes `packages/cli/src/settings/` (NMU-012), with its constants in
`config/settings/` and its types in `types/settings/`. The target: keys are words gspot defines, so no key needs
quotes; a value that loosens a check carries its reason next to it as `{ value = ..., reason = "..." }`; every path is
relative to the repository root, and record lists live only at the root. Each setting is declared once, in
TypeScript, as a zod schema, and the same schemas write `gspot.schema.json`, which ships in the npm package and is
linked at the pinned version. The sections after the findings give the format rules, every table and key, an
example file, the code layout, and how other tools design their settings files.

## Findings

### POL-001: A code generator writes 827 lines of schema code so that settings have TypeScript types

- Where: `packages/cli/src/policy/schema/native/public.ts` (533 lines, generated), `packages/cli/src/policy/schema/native/contracts.ts` (294 lines, generated), `packages/cli/src/policy/schema/contracts.ts:13-99,207-243` (`compileSettingFields`, `compileSettingField`, `compileSettingPrimitive`, `compileStringSetting`, `compileNumberSetting`, `compileSettingValue`), `packages/cli/src/generation/compilation/public.ts:137-174,269-333` (`compiledSetting`, `schemaFields`, `namingSchemas`, `schemaModule`, `settingSchemaSources`), `packages/cli/src/generation/compilation/contracts.ts:26-63,122-297` (`unwrapSetting`, `childSetting`, `settingChildren`, `nativeSetting`, `compileNamespace`, `validateDefaults`, `effectiveNamespace`, `requiredSettings`, `publicToolTables`), `packages/cli/src/config/policy/setting-values.ts`, `packages/cli/src/types/policy/setting-values.ts:14-18` (`CompiledSetting`), `scripts/setting-values.ts`, `packages/cli/scripts/build.ts:20-26`, `gspot.toml:270` (knip entry), `tests/cli/parsers/setting-values.test.ts` (124 lines), `packages/cli/src/parsers/schema/contracts.ts:177-240` (the manifest `type`/`items`/`validation` language)
- Kind: delete
- Problem: The type of each setting is written in a small language inside `manifest.toml` (`type`, `items`, `validation`, `path_role`). A compiler turns that into zod schema objects at run time and into zod source text; a script writes the text into `policy/schema/native/`, and the build fails when the text is stale. Each validator is built twice. The generated file repeats one line 151 times, once for every language and category pair of `naming.*.max_chars`, `max_words`, and `case`. Root settings go the other way: zod schema to JSON Schema to a declaration (`declarationOf`). So two pipelines convert between three type systems for one concept, in about 1,470 lines across 121 manifest `[[setting]]` entries.
- Fix: Delete `policy/schema/native/`, the compile functions, `settingSchemaSources` and the functions it calls in `generation/compilation/`, `config/policy/setting-values.ts`, `CompiledSetting`, `scripts/setting-values.ts`, its build step, its knip entry, and `tests/cli/parsers/setting-values.test.ts`. Write one zod schema per settings table by hand: the configuration tables in `packages/cli/src/settings/schema/tables.ts`, the `[tools.<tool>]` tables in `settings/schema/tools.ts`, with `z.partialRecord(language, ...)` for per-language limits and naming (S09-006). Move every `[[setting]]` declaration out of the manifests: each setting is declared once in TypeScript beside its schema, with its default, its per-language defaults, and its level-`all` value; the static values sit in `config/settings/` topic files, and the manifests carry none of them. The declaration type is S09-012; `declarationOf` fills `default` and `default_all` from the schema. The table types are written by hand in `types/settings/tables.ts` and `types/settings/tool-tables.ts`; each schema is checked against its type by the type rule (`satisfies SchemaShape<T>` on object literals, `satisfies z.ZodType<T>` otherwise), and no exported type uses `z.infer`. Keep the one useful check of the compiler: each default parses with its own schema (`validateDefaults`). Do after TPP-011 and TPP-040, which first delete the freshness test and the two field-list tests.

### POL-003: `gspot set` on a table setting deletes every other entry

- Where: `packages/cli/src/commands/set.ts:71-100,138`; today's table settings `words`, `naming.allowed`, `naming.reserved`, `licenses.exceptions`, `tools.knip.ignore_dependencies`, `tools.purgecss.safelist`, `tools.v8r.schemas`, `tools.eslint.rules`, `tools.eslint.import_extensions`, `tools.eslint.runtimes`, `tools.*.rules`, `architecture.roles`; `docs/src/content/docs/guides/policy.md:101-104`
- Kind: fix-bug
- Problem: For a setting of type `table`, `parseSettingValue` returns a single-value change, and `setKey` replaces the whole table. `gspot set words '{"Acme":"Our product name."}'` removes every other accepted word. `gspot set words Acme` is refused (a string is not a table), and `gspot set words.Acme ...` is an unknown setting. So the guide's "Adding ... accepted words needs a reason" has no safe command. Lists do not have this problem: `set` appends to lists. `tests/cli/commands/set/reasons.test.ts:52` relies on `set naming.allowed '{}'` wiping the table.
- Fix: `gspot set` merges the given entries into a table setting that stays a table (`tools.<tool>.rules`, the value of `tools.<tool>.extra`) instead of replacing it. `gspot unset <setting> <entries...>` removes the named entries; to replace a whole table, unset it and set it again. The other maps become lists or records (TMF-007, TML-005, TML-008, TML-009), and `set` adds list items as it does today. `gspot set` never writes a `[[...]]` record list: you write record lists by hand, `gspot ignore` and `gspot unignore` write `[[ignore]]`, and `gspot add --scope` and `gspot remove --scope` write a scope's configurations. Delete the test case at `tests/cli/commands/set/reasons.test.ts:52`.
- Size: medium

### POL-004: Quoted keys: why TOML needs them, and one rule that removes them

- Where: every map whose keys are user data (below); this repository's `gspot.toml:15,18,174-194,199,267,273-276` (13 quoted keys or headers)
- Kind: simplify
- Problem: In TOML a key without quotes may use only letters, digits, `_`, and `-`. Outside quotes, `a.b` means "key `b` inside table `a`", and `@` is not allowed at all. So `lightningcss@1.33.0` without quotes is refused, and every key that holds something the user names needs quotes: `[scope."<path>"]`; `[check."<name>"]` (the docs teach names with `/`, so `[check."project/notes".output.fields]`); `[licenses.exceptions."<package>@<version>"]`; `[reasons]` keys (a setting name has dots); `[words]` and `[naming.allowed]` keys with `.`, `'`, `$`, or a space; glob keys of `tools.eslint.import_extensions`, `tools.eslint.runtimes`, and `tools.v8r.schemas`; regular expressions and npm packages with a scope in `tools.knip.ignore_dependencies` (`gspot.toml:276` is a 600-character quoted header); Tailwind classes in `tools.purgecss.safelist`; and namespaced rule IDs in the rule-option tables. The monorepo guide has to say "Quote a key that contains slashes" (`monorepos.md:31`).
- Fix: One rule for the whole file: a key is a word gspot defines; anything the user names (a path, a check, a package, a version, a word, a glob, a setting name) is a value. The only keys that are not gspot's words are a tool's rule IDs under `tools.<tool>.rules` and option names inside `tools.<tool>.extra`, which mirror the tool's own file; quotes appear only for namespaced rule IDs such as `"@typescript-eslint/no-explicit-any"`. The rule is applied by POL-006 (`[[scope]]`), POL-007 (`[[command_check]]`), CFR-002 (the reason form replaces `[reasons]`), TML-005 (`naming.reserved` and `naming.allowed` go), TML-008 (`tools.eslint.import_extension`, the `runtime` field, `[[tools.v8r.schema]]`), TML-009 (`[[licenses.allowed_package]]`), and TMF-007 (three plain allow-lists). Trade-off: a record takes one or two more lines than a map entry, and a list can hold duplicates, so gspot refuses two `[[scope]]` records with one `path` and two `[[command_check]]` records with one `name` (it already checks scope duplicates, `errors/contracts.ts:89-103`).
- Size: large

## Rules of the format

1. **One file.** `gspot.toml` at the repository root, TOML 1.0. The first line is the `#:schema` line with the
   running version. There is no `version` key, no `extends`, and no tool version. Each inline table stays on one line.
2. **Keys are words gspot defines**, in snake_case whole words. Anything you name (a path, a check, a package, a
   version, a word, a glob, a setting) is a value, so no key needs quotes. The only exceptions are a tool's rule IDs
   under `tools.<tool>.rules` and option names inside `extra`, such as `"@typescript-eslint/no-explicit-any"`.
3. **Plural lists, singular records.** A list key names its items in the plural (`configurations`), unless the table
   already names them (`licenses.allowed`) or the tool owns the name (`tools.trivy.severity`). A record header is a
   singular noun, because each block is one record.
4. **Paths.** Every path you write is relative to the repository root, also inside a `[[scope]]`. A shipped default
   path applies inside the folder of the scope that selects its configuration; `gspot list settings` shows it joined
   to that folder.
5. **Record lists live at the root.** The eleven record lists are `[[scope]]`, `[[command_check]]`, `[[ignore]]`,
   `[[naming.override]]`, `[[format.override]]`, `[[tools.eslint.override]]`, `[[architecture.module]]`,
   `[[licenses.allowed_package]]`, `[[coverage.target]]`, `[[site.size_limit]]`, and `[[tools.v8r.schema]]`. Their
   `paths` say where they apply. A `[[scope]]` holds only single values and value lists, as dotted keys. gspot refuses
   a record list inside a scope: "Write [[naming.override]] at the root. Its paths say where it applies."
6. **Inheritance and who writes what.** A scope gets the root value and the value of every scope that contains it. A
   single value takes the nearest one. A list adds up without repeats; a scope cannot clear a list it inherits, so to
   stop a check in a folder, write an `[[ignore]]` with `paths`. A rule-option table merges rule by rule. A command
   (any value of the command type) replaces the inherited one. `gspot set` writes the same shapes: it replaces a
   single value or a command whole, adds items to a list, and merges entries into a table; `gspot unset` removes a
   value, list items, or table entries. `gspot set` never writes a record list: you write record lists by hand,
   `gspot ignore` and `gspot unignore` write `[[ignore]]`, and `gspot add` and `gspot remove` (with `--scope` for a
   scope) write `configurations` and `removed_configurations`. An item of `tools.eslint.restricted_imports` is one
   inline table, such as `{ name = "lodash", message = "Import the function from lodash-es." }`.
7. **Reasons.** A setting that loosens a check is written `{ value = ..., reason = "..." }`; any other setting is a
   plain value, and gspot refuses the reason form on it. A record that loosens a check has a `reason` field. One
   reason covers the whole value written at one level (the root or one scope); lists add up across levels, and each
   level keeps its own reason. `gspot set --reason` writes the reason form; adding an item that loosens the check
   without `--reason` is refused (TMF-006). `gspot unset` removes a value and its reason together. These settings
   take the reason form:
    - when raised: the limits, the name lengths, and `tools.svgo.min_saving_percent`;
    - when lowered: the coverage settings, `dependencies.min_release_age_days`, and `limits.min_function_statements`;
    - `structure.reexports = "index-only"`;
    - for each item the shipped list lacks: `allowed_words`, `naming.cases`, `dependencies.allowed_registries`,
      `docs.allowed_urls`, `site.allowed_unlisted_pages`, `tools.knip.ignore_dependencies`, and
      `tools.purgecss.safelist`;

    - always: every `extra` table.

    No other setting takes it. The rule-option tables (`tools.<tool>.rules`) never do: turning a rule off is refused,
    and accepting a finding is an `[[ignore]]`. Lists that turn a check on take no reason (`licenses.allowed`,
    `xcode.allowed_entitlements`, `tools.codeql.languages`, `html.templates`, and the other settings of rule 8), and
    neither do lists that describe the project (`test_files`, the `architecture.roles` lists, `tools.commitlint.types`,
    `tools.knip.entry`).

8. **No "off" values.** A missing key means the default. To stop a check, or one rule of it, write an `[[ignore]]`.
   For example, a repository without a license file ignores rule `missing-license` of `docs/required-files`. Twelve
   settings feed a check that waits for them and does not run, or reports nothing, without them; the Default or
   Meaning column of each says so: `licenses.allowed`, `tools.codeql.languages`, `xcode.allowed_entitlements`,
   `html.templates`, `translations.messages_folder`, `openapi.document`, `openapi.generate_command`,
   `supabase.types_file`, `postgres.client_schemas` (outside Supabase), `architecture.roles.environment_readers`,
   `tools.semgrep.rule_files` (when no configuration gives rules), and `[[site.size_limit]]`.
9. **Which files gspot reads.** The files Git tracks, plus untracked files that `.gitignore` does not hide. Mark
   generated and copied files `linguist-generated` or `linguist-vendored` in `.gitattributes`.
10. **One declaration.** Each setting is declared once, in TypeScript, as a zod schema beside the settings code
    (POL-001), with its default, its per-language defaults, and its level-`all` value. The same schemas write
    `gspot.schema.json`: strict (no unknown key), every key with a description and its default, `reason` marked
    required, dates as `format: date`, and `anyOf` for the reason form. The declaration type `SettingDeclaration` has
    the fields of S09-012.

**Root only:** `level`, `allowed_words`, `tool_timeout_seconds`, `[hooks]`, `[ci]`, `[rules]`, `[structure]`,
`docs.banned_headings`, and the eleven record lists. **Root and scope:** `configurations`,
`removed_configurations`, `test_files`, and every other table.

## What gspot init writes

For a TypeScript repository on GitHub with hooks on (`ci.provider` is not written, because `github` is its default):

```toml
#:schema https://unpkg.com/@gspothq/cli@0.1.0/gspot.schema.json

# gspot settings for this repository. Change them with gspot set, unset, ignore, add, and remove.

configurations = ["typescript"]

[hooks]
enabled = true

[ci]
enabled = true
```

`gspot init` shows these values in its plan and asks only "Continue?" (`--yes` answers it). It asks no question about
hooks, CI, or rules. Turn CI on or off later with `gspot set ci.enabled true` or `false`; on GitLab also run
`gspot set ci.provider gitlab`.

## Example

A TypeScript and Python repository with a Postgres database, an API service, and a docs site. It shows the schema
line, root keys, the hooks and CI switches, the reason form for a single value, a list, and an `extra` table (header
spelling), two scopes with dotted keys and a root-relative path, and five record lists.

The blocks are in the order gspot's writer emits them (POL-013), so `gspot set` does not reorder the file and
`gspot/settings-format` accepts it: the root keys; then the tables in the order `hooks`, `ci`, `rules`, `format`,
`limits`, `naming`, `architecture`, `structure`, `dependencies`, `docs`, `licenses`, `spelling`, then the other tables
from A to Z, then `tools`, each table followed by its own record lists (`[[naming.override]]` sits where `[naming]`
would, `[[licenses.allowed_package]]` right after `[licenses]`); last the top-level record lists `[[scope]]`,
`[[command_check]]`, and `[[ignore]]`. The file parses with smol-toml 1.9.0, has no quoted key and no inline table
that spans lines, and taplo 0.10.0 `check` and `fmt --check` accept it with `.gspot/config/taplo.toml`; a plain
`taplo check` fails only while the schema link is 404 (CFR-001).

```toml
#:schema https://unpkg.com/@gspothq/cli@0.1.0/gspot.schema.json

# gspot settings for this repository. Change them with gspot set, unset, ignore, add, and remove.

level = "all"
configurations = ["typescript", "python", "postgres"]
removed_configurations = ["jest"]
allowed_words = { value = ["Acme", "OAuth", "PostgREST"], reason = "Our product name and two protocol and tool names the docs use." }

[hooks]
enabled = true

[ci]
enabled = true
setup_command = ["npm", "ci"]

[limits]
function_lines = { value = 80, reason = "The migration planner is one state machine; a split hides the order of its steps." }

[[naming.override]]
paths = ["services/api/migrations/**"]
categories = ["files"]
allow_digits = true
reason = "Migration file names start with their version number."

[licenses]
allowed = ["MIT", "Apache-2.0", "BSD-3-Clause", "ISC"]

[[licenses.allowed_package]]
name = "lightningcss"
version = "1.33.0"
reason = "MPL-2.0. A build tool of the docs site; we ship none of its files and change none."

[tools.prettier.extra]
value = { bracketSpacing = false }
reason = "The team keeps the old object spacing, so one upgrade does not reformat every file."

[[scope]]
path = "services/api"
configurations = ["fastapi", "pytest"]
coverage.lines = 90

[[scope]]
path = "docs"
configurations = ["astro", "site"]
site.build_folder = "docs/out"

[[command_check]]
name = "notes"
command = ["node", "scripts/check-notes.mjs", "{files}"]
paths = ["notes/**"]
stage = "commit"

[[ignore]]
check = "dependencies/osv"
rule = "GHSA-ch52-4w7c-c8xp"
paths = ["package-lock.json"]
reason = "No fixed release exists yet; only the docs build uses the package."
until = 2026-11-08
```

What the comparison shows, and what gspot takes from it:

- **Format follows the ecosystem.** Rust and Python tools, and tools that serve every language and write their own
  file (mise, Taplo, lefthook's TOML form), use TOML; JavaScript tools use JSON or JavaScript; CI tools use YAML.
  gspot stays on TOML 1.0.
- **"Turn on" is a baseline plus detection**, with an off list that stops detection from coming back (Biome preset
  and domains, golangci-lint `default` and `disable`, Trunk `lint.disabled`). gspot's `level`, detection, and
  `removed_configurations` match this.
- **Per-path settings are records with a path field** in the newer designs (Biome 2, ESLint flat config, Prettier,
  golangci-lint v2, Taplo, REUSE, Trunk). Maps keyed by path or glob remain in older files, and those are the files
  with quoted keys. gspot uses records.
- **Exceptions with a reason are rare, and with an end date rarer.** Only security tools have both: OSV-Scanner
  (`reason`, `ignoreUntil` as a TOML date), Trivy (`statement`, `expired_at`), and cargo-deny (`reason`, `expiry`).
  gspot's `[[ignore]]` with a required `reason` and an optional `until` matches them.
- **Unused exceptions get reported** (golangci-lint `warn-unused`, ESLint `reportUnusedDisableDirectives`, Ruff
  RUF100, cargo-deny `unused-allowed-license`, pre-commit `check-useless-excludes`); gspot has
  `gspot/unused-entries`.
- **Versions sit outside the settings** in most tools: package.json and the lockfile pin Biome, ESLint, Prettier,
  Knip, Turborepo, Nx, and Ruff. MegaLinter fixes every linter with one image tag, the closest match to gspot: one
  gspot version is one tested set of tools. A key named `version` is ambiguous (the file format in golangci-lint,
  Trunk, Dependabot, and REUSE; the tool in mise, lefthook, and Ruff), so gspot has none.
- **Schemas.** 20 of the 25 publish one; Biome and Knip put the version in the URL, and Taplo reads a `#:schema`
  line in any TOML file.
- **Short files come from defaults, presets, and inheritance**, not from clever syntax.
