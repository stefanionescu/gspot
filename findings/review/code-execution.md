# Code Review: Execution, Tools, Parsers, Platform, Repository, Checks

19 unresolved review records remain.

A read-only review wrote these findings on October 6, 2026, against commit `3e1445a2d`. The Existing column names an older record that covers the same problem.

The worst problems first:

1. Python and Swift checks build a multi-megabyte cache key on every call. `JSON.stringify([root, files])` serializes the 4 KB `prefix` Buffer of every tracked file (`parsers/python/source.ts:137`, `parsers/swift.ts:88`).
2. `configuredChecks` and `planRun` disagree on `replaces`. A Next.js check in one scope hides `typescript/tsc` in the root scope, but only for generation and `explain`. `planRun` still runs it there (`execution/planning/plan.ts:163` vs `:188`).
3. Gspot keeps four ways to copy source into a temporary folder. The revision copy holds the whole repository in memory about 2.3 times over and fsyncs every file. `createFileWorkspace` keeps every file's bytes in memory.
4. Some code serves almost nothing. `repository/revisions/push.ts` re-implements Git fetch refspecs (about 160 lines). `parsers/vale.ts` is a 100-line INI parser for a file gspot writes itself. `parsers/lockfiles.ts` has seven lockfile readers that serve one sub-check.
5. `tools/locate.ts:155` `miseVersion` can never match.
6. Format quirks of the output parsers are spread over five files. The `eslint` format duplicates the generic `json` format.
7. `openRoot` (`platform/root/*`) is justified for lifecycle writes. Gspot also uses it for scratch folders it creates itself. `readSource` opens a new root on every read.

These parts are sound:

- `platform/spawn.ts` (execa plus process-group kill, which execa lacks).
- The built-in check table (`checks/registry.ts`; every entry maps to a manifest check, and every command-less check has an entry).
- The `tools/` files `locate`, `inspect`, and `mise`, which do separate jobs.

`tools/pins.ts` is manifest math and moves to `configurations/pins.ts` (review/source-layout/003).

## Simpler designs

### 1. One scratch copier

Today gspot has four copiers, with different rules for links, memory and modes:

- `execution/snapshot/workspace.ts:126-144` `createFileWorkspace` reads every file into memory.
- `workspace.ts:155-191` and `:32-118` `scratchCopy` copies files, clones `node_modules` and `.venv`, and repoints links.
- `execution/snapshot/installed.ts:124-181` and `:22-48` copy dependencies with junctions, unlinking links that do not resolve and refusing links that leave.
- `execution/snapshot/revision.ts:43-73` writes blobs through `Root.write`.

Proposal: one `copyIntoScratch({ root, paths, dependencies: 'clone' | 'link', blobs? })`. It copies files with `copyFileSync` or writes blobs with `writeFileSync`. It has one link policy: keep a link that resolves inside the copy, clone or repoint one into a copied dependency tree, and refuse one that leaves. Fixers read originals for changed paths only.

- Files deleted: none whole. `installed.ts` shrinks to the package manifest and lockfile guard and Vale packages.
- Saving: about 150 lines. Gspot also stops holding the repository in memory and stops one fsync per file on push.

### 2. Push selection by Git

Today `repository/revisions/push.ts:20-140` parses fetch refspecs, validates every pattern with `git check-ref-format`, lists all refs, applies wildcard capture and negative refspecs, then peels each object with two spawns (`:160-168`).

Proposal:

- For a new ref, run `git rev-list <object> --not --remotes=<remote>`. Use `--remotes` with no name when Git gives no remote. This is the form in Git's sample pre-push hook. Get the changed paths with the same `--not` arguments to `git log --name-only`.
- Peel all pushed objects in one `cat-file --batch-check`.
- Behavior change: custom fetch mappings outside `refs/remotes/<remote>/` are not counted as "already on the remote." That is rare, and the cost is only scanning more commits.

Files deleted: the refspec types in `types/repository/revisions.ts:34-38`, `REFSPEC_FIELDS`, and `tests/cli/repository/refspecs.test.ts`. Saving: about 160 lines.

### 3. Vale packages from a constant

Today `parsers/vale.ts:15-117` (an INI reader) and `tools/vale.ts:17-21` read the `Packages` line back from the `vale.ini` gspot wrote from `vale.ini.tmpl:2,113`.

Proposal: export `VALE_PACKAGES` from a constants file. The Eta source and `hasValePackages` and `installValePackages` all read it. `PACKAGE_FOLDERS` (Harper's dictionaries) stays.

- Files deleted: `config/parsers/vale.ts` (except `PACKAGE_FOLDERS`, which moves), the `ValeAssignments` and `LineCursor` types, and the `parseValePackages` tests.
- Saving: about 120 lines.

### 4. License exceptions checked against the license scan

Today `checks/general/structure/stale-allowlists.ts:71-118` parses up to seven lockfile formats (`parsers/lockfiles.ts:27-133`, nine schemas in `parsers/schema/lockfiles.ts:20-39`). It only proves that each `licenses.exceptions` package and version exists.

Proposal: `licenses/packages` (`checks/general/licenses.ts:126-151`) already gets every installed `name@version` from license-checker or pip-licenses. Report an exception that matches no scanned package as stale there. `parseLockfile` and `rootLockDependencies` stay for the npm tool project.

- Files deleted: `lockedPackages`, `LOCK_READERS` and `tests/cli/parsers/lockfiles.test.ts`.
- Saving: about 170 lines.
- Trade-off: the staleness finding then needs installed dependencies, as the license check already does.

### 5. One description per output format

Today format knowledge lives in five places:

- `parsers/output/parse.ts:125-142` `FORMAT_READERS`
- `execution/output.ts:69-71` (format list), `:83-99` (TruffleHog) and `:153-154` (typos and markdownlint)
- `config/execution/output.ts:2`
- `execution/command/runner.ts:75`

On top of that, `eslint` duplicates `json` (`parsers/output/reports.ts:105-131`).

Proposal: `FORMATS: Record<format, { read, namesFiles, verifyFiles, withholdOutput }>` in `parse.ts`. `json` gains a `fixable` field mapping, and `format = "eslint"` becomes json.

- Deleted: `eslintFindings`, `eslintReportSchema`, `eslintDiagnosticSchema`, the `EslintReport` and `EslintDiagnostic` types, and `FILELESS_FORMATS`.
- Saving: about 70 lines. A new format becomes a one-place change.

### 6. `openRoot` only where gspot writes into the repository

Today `platform/root/*` (624 lines) is used:

- for lifecycle writes and the Swift build-cache claim, where it is justified;
- for every source read (`platform/source.ts:16,43`, one `openRoot` per read);
- for the scratch folders gspot creates with `mkdtemp`: ESLint request and result, Jest reports, Vale package installation, the site build folder, installed trees, the revision copy, and the dependency copies.

Proposal:

- Keep `openRoot` for writes into the repository and for the build cache.
- Reads use one cached real root plus `isInside`.
- Scratch folders use plain `node:fs`.
- `walkRoot` users on scratch folders switch to `readdirSync(dir, { recursive: true })`.
- `close` goes.
- Settings validation leaves `rules.ts` (review/code-execution/009).

Saving: about 80 lines, and about two realpath calls fewer per file read.
