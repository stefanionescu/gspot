# Commands and Templates

26 unresolved review records remain.

A read-only review wrote these findings on October 6, 2026, against commit `3e1445a2d`. The Existing column names an older record that covers the same problem.

Worst problems first:

1. A template drops most of a real customization.
    - Export removes every entry that has a path-named key, plus five whole tables.
    - On this repository's `gspot.toml` it leaves out 65 items and keeps 21. It drops 9 of 11 ignores, every exclude, every structure path entry, every `naming.fixed_keys` entry, all architecture modules and roles, and all 4 scopes.
    - The owner wants a repository's own ignores and path entries carried ("custom exceptions, all that").
    - `structure/stale-allowlists` (level `recommended`) already reports carried paths that match nothing, so the stripping is not needed.
2. Command checks (`[[check]]`) cannot travel. Export drops them, and the template schema refuses them.
3. `init --from` writes schema defaults into the new `gspot.toml` as authored values: `require_reasons = false`, the 10 default `tests` globs, the full `agent_rules` table, `hooks.push_files`, and `ci.platforms`/`ci.files`. It merges zod output instead of the template text.
4. The path filter is a key-name list (`PATH_KEYS`) kept beside the schema. It drops portable values (`agent_rules.instruction_files`, `agent_rules.exclude`). It keeps real repository paths (`semgrep.rule_files`, `tools.knip.entry`, `vitest.config_file`, `tools.eslint.script_files`). As a result, the help text "settings that name a path stay out" is wrong in both directions.
5. Export records its file in the ownership log, and that log is never committed.
    - As a result, a committed template cannot be exported again from a fresh clone or after a hand edit.
    - Export also refuses any destination outside the repository.
    - The exported file is not formatted, so the repository's own `files/taplo-format` check reports it.
6. `gspot set hooks.push_files --default` turns hooks off, because an empty `[hooks]` table is deleted and table presence is the on/off switch.
7. Policy edits split two ways: `add` and `remove` install tools, while `set`, `ignore`, and `apply` do not. "Nothing to remove" exits 2 in `remove` and 0 in `ignore --remove` and `set --remove`.
8. Help text is hand-written 12 times and parsed back by the docs build. Two reference pages link source files that do not exist (`commands/add.ts`, `commands/remove.ts`).

## Template flow

### a. What goes into an exported template

The template keeps `level`, the root `configurations`, `run_with`, `require_reasons`, `tests`, `tool_timeout_seconds`, `limits`, `format` (without `overrides`), and `dependencies` (without `ranges_allowed`). It keeps `licenses` (allowed lists and exact-version exceptions), the `naming` lists (`banned`, `allowed`, and the language groups), and `prose.vocabulary`. It keeps `[hooks]` (an empty table too), `[ci]`, and `agent_rules.enabled`. It keeps every `tools.*` setting and `verbatim` table whose key path has no name from `PATH_KEYS`, every `[[ignore]]` without `paths`, `architecture.imports_allowed`, and `structure.reexports`.

It leaves out every `[[scope]]` (including its configurations and settings), `generated`, `vendored`, root `exclude`, every `[[check]]` (command checks), and every `[[ignore]]` with `paths`. It also leaves out every `tools.*.exclude`, every `tools.codeql.ignore` entry, and `tools.eslint.overrides`/`format.overrides`. On the structure and naming side it drops `structure.*_allowed`, `naming.fixed_keys`, `naming.paths`, `architecture.modules`, and `architecture.roles`. From `agent_rules` it drops `folder`, `project_folder`, `instruction_files`, and `exclude`. It also drops any `module` that starts with `.` or `/`.

The stated reason is "settings that name a path stay out" (`export.ts:59`). The rule is a list of key names, not the schema, so it misses many path settings and catches some that are not paths (findings above). Yes, it drops most of a real customization.

This repository's `/gspot.toml` as the worked example (simulated with the same rules):

- **Survives (21):**
    - `level = "all"`
    - the 19 root configurations
    - `run_with`
    - `dependencies.scanner`
    - `licenses.allowed` (12)
    - `licenses.exceptions` (7, pinned to exact versions of this repository's lockfile)
    - `naming.banned` (26)
    - `naming.allowed` (4)
    - `tools.taplo`
    - `[hooks]`
    - `tools.typos.words` (5)
    - `tools.eslint.import_extensions`/`script_files`/`node_version`
    - `tools.commitlint.scopes` (this repository's scope names)
    - `tools.knip.entry` (this repository's files)
    - `tools.knip.ignore_dependencies` (4, one tied to workspace `tests`)
    - `tools.codeql.languages`
    - `architecture.imports_allowed` (16 edges that now point at no module)
    - the 2 Open Source Vulnerabilities (OSV) `[[ignore]]` entries without paths
    - `prose.vocabulary` (156)
- **Left out (65):**
    - the 4 scopes (with docs/tests configurations such as astro, zod, cloudflare, jest, vitest)
    - all 16 `naming.fixed_keys`
    - `tools.lychee.exclude`
    - both `tools.typos.exclude`
    - `tools.jscpd.exclude`
    - `tools.eslint.rules."gspot/instances-in-registry"`
    - all 5 `tools.codeql.ignore`
    - both `docs.exclude`
    - all 16 `architecture.modules`
    - `architecture.roles`
    - 10 of 12 `[[ignore]]` entries
    - all 8 `structure.*_allowed` entries

The kept part is mostly the shared lists. The ignores and path entries, which are the work a team does in a repository, do not travel. Several kept items are repository-specific anyway.

### b. How init takes a template

- **Flag:** `gspot init --from <template>` (`init/command.ts:115`).
- **Sources** (`policy/templates.ts:169-174`):
    - A local path, resolved from the working directory.
    - An `https://` URL, with a 10 s timeout. `http://` is refused.
    - `github:owner/repo[/path][@ref]`, which maps to `https://raw.githubusercontent.com/owner/repo/<ref or HEAD>/<path or gspot.template.toml>` (`templates.ts:71-76`; `RAW_HOST`, `GITHUB_PREFIX`, `TEMPLATE_FILE` in `config/policy/templates.ts:26-30`). No token is sent, so private repositories return 404.
- **Answers:** the template fills init's answers: configurations, hooks (whether `[hooks]` exists), the CI provider, `run_with`, and `agent_rules.enabled` (`init/command.ts:25-36`).
    - Explicit flags win (`init/command.ts:76`).
    - Then the template tables are merged into the new policy (`policy-text.ts:34-46`).
    - Because init merges zod output, defaults come along with them (finding above).
- **Settings that do not apply:** every template configuration stays selected in both modes, even when the destination has no matching files (`lifecycle/selection.ts:74`).
    - They are recorded as manual choices, so `apply` keeps them (`configuration-overrides.ts:83-91`).
    - `detect` only adds the detected configurations on top.
    - Their settings stay in gspot.toml unused. Their checks find no inputs.
- **Recording:** the template is copied once. `template` and `selection` are stripped (`config/commands/init.ts:25`). The sha256 is only printed in the plan. Nothing links the repository to the template, and `apply` cannot refresh from it. A repository that already has gspot.toml cannot take a template, because init refuses (`init/command.ts:67-72`).

### c. Command checks

A repository adds its own tool with `[[check]]` in gspot.toml (`policy/schema/policy.ts:98-136`). An entry declares the command, globs, stage, fix command, finding exit codes, output parser, needs, and platforms. gspot does not install that executable: the entry has no pin.

Shipped tools can take extra native options through `tools.<tool>.verbatim`. Templates do not carry `[[check]]`: export drops it, and the template schema refuses it. `verbatim` tables do travel, unless a key inside matches `PATH_KEYS`. A command check whose tool gspot pins and installs is not supported anywhere.

### d. Gaps against the owner's requirement, with the smallest fix for each

1. A repository's own ignores and path entries are dropped. Stop stripping, and rely on `gspot/unmatched-paths` (today `structure/stale-allowlists`) in the destination to flag paths that match nothing.
2. Command checks are dropped. Remove `check` from `REPOSITORY_TABLES` (also `generated`, `vendored`, `exclude`). Keep only `scope` out.
3. The path filter is wrong in both directions. Deleting it closes gaps 1 and 2 and removes about 75 lines.
4. Init writes schema defaults into the new policy. Merge the raw template TOML.
5. A template cannot be refreshed from the source repository in a new clone, and cannot be written outside the repository. Write the exported file directly, without the ownership log.
6. The exported file fails the source repository's TOML format check. Write it through the same layout as the policy.
7. A repository that already uses gspot cannot take a template. Decided on October 6, 2026: templates are copied once (`review/commands-templates/009`). To take a template, delete gspot.toml, then run `init --from`.
8. Template origin is not recorded. Decided on October 6, 2026: init writes one comment line with the template name and sha256 (`review/commands-templates/009`).

### e. File format

The format is TOML in the same shape as gspot.toml. `templateSchema = policySchema.omit({scope, generated, vendored, check, exclude}).extend({template, selection})` (`policy/schema/templates.ts:7-17`). `parseTemplate` also refuses any `PATH_KEYS` key anywhere (`templates.ts:153-157`). As a result, a template is a portable gspot.toml with three differences:

- **Required `template` name:** only shown in the init plan. Not needed: use the file name.
- **Required `selection`:** `exact` or `detect`. The meaning is needed, but `exact` can be the default, because export always writes it.
- **Five missing tables and the path-key ban:** not needed except `scope` (gaps 1 and 2).

With those three changes, any gspot.toml without `[[scope]]` is a valid template, and export is close to a copy with a report.

### f. Naming

User-facing terms already agree:

- "template" for the file (docs page "Reuse templates," `--from <template>`, error code `template`, `TEMPLATE_FILE = gspot.template.toml`).
- "export" for the verb.
- "profile" does not appear in source or docs. It survives only in old finding records (`areas/integration-tests/015`, `063`, `072`), which cite renamed files.
- "preset" means ESLint presets only.

The file name is not consistent. Help and docs use `<name>.gspot.template.toml`, the GitHub default is `gspot.template.toml`, and the tests use `<name>.template.toml`. The name derivation mishandles the documented form.

Inside the code, "template" also means the Eta sources of tool files (`generation/templates.ts`, `types/generation/templates.ts`, `config/generation/templates.ts`, the manifest `template` key, `.tmpl` files) and two settings (`env.templates`, `html.templates`).

Recommended names:

- Keep "template" for the feature and "export" for the command.
- The file is `<name>.template.toml`, and the name strips `.template.toml`, as the code and the tests already do (`review/docs-site/005`). The GitHub default stays `gspot.template.toml`.
- Keep `policy/templates.ts` as the one source module for policy templates.
- Rename the Eta names as review/glossary/001 says: `.eta` sources, the manifest field `source`, and `eta.ts`, so template means only the file export writes.

## Overlap between commands

- **set, ignore, add, and remove:** one pipeline. Each builds a `Mutation` and goes through `preparePolicy`, then `proposePolicy`, then `commitPolicy` or `previewPolicy` (`commands/policy-edit.ts`, `policy/edit.ts:48-61`). `apply` reuses `preparePolicy`/`writePolicy`/`writeOutputs` with reconciliation in between. Its policy can be unchanged and it still must write the generated files, so it cannot use `commitPolicy`. Differences:
    - `add`/`remove` also record the history of manual choices and install tools (`configurations.ts:29-84`).
    - The history of manual choices is built with a choices map that two other modules build again (finding above).
    - `ignore` keeps its own entry matcher.
- **list, explain, and doctor:** `explain` is about one subject and does not overlap. `list` and `doctor` both print "detected, not selected" from the same function (finding above). `doctor`, `check`, and `apply` all run the re-detection. Drop it from `check`.
- **install, apply, and init:** the split is clear.
    - `init` = detect, write the policy, apply, install.
    - `apply` = write the generated files, no tools.
    - `install` = tools from lockfiles plus `core.hooksPath`.

    The blur is that `add`/`remove` install and `set`/`ignore` do not (finding above).
