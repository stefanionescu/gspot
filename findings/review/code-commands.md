# Commands, Lifecycle, Policy, Generation, Rules, Output, Configurations: Code Review

43 unresolved review records remain. IDs and verification evidence are retained in the JSON checklist.

A read-only review wrote these findings on October 6, 2026, against commit `3e1445a2d`. The Existing column names an older record that covers the same problem.

Reviewed at HEAD 3e1445a2d on 2026-10-06. Every file in the area was read in full.

Worst problems first:

1. Changing one key costs about 30 source files. `gspot set level all` reads gspot.toml 5 times, validates it 3 times, and builds the full repository inventory twice. Six other code paths read or write gspot.toml their own way, and three TOML serializers format it.
2. Two real bugs in pruning. Removing `[hooks]` leaves the hook scripts and `core.hooksPath` in place, so the hooks keep running. With `agent_rules.enabled = false`, `apply --dry-run` says nothing changes, but `apply` deletes the rule files.
3. The reason rules differ between `gspot set` and gspot.toml validation. `explain` states a third version.
4. The history of manual choices (`selections` in the ownership log) is computed by four functions in four files. They must run in a fixed order. The language/framework test is copied 6 times.
5. The ownership layer is about 1,070 lines. It holds a crash journal, file modes, an `export` kind, and 9 overlapping "changed while running" checks on top of the compare-and-swap write. `ApplyReport.preserved` and its notes never reach the user.
6. Generation keeps the same facts in two or three places:
    - package.json redirects (two hand-written generators)
    - glob escaping (four copies)
    - ESLint level membership (plugin, JSON list, TypeScript)
    - Eta inputs (the ScopeView members copied one by one)

No backward-compatibility shims, migrations, or aliases for old names exist in this area. The ownership schema is `version: 1` only.

## Simpler designs

### 1. One policy edit function

Today: changing one key spans `commands/set.ts` (257 lines), `commands/policy-edit.ts` (151), `policy/edit.ts` (161), `commands/ignore.ts` (182), `commands/configurations.ts` (219), and the serializers in `commands/init/policy-text.ts:68-72` and `policy/templates.ts:101-130`. `gspot set level all` passes through about 30 source files. They are program, set, session ×2, read, normalize, 5 schema files, 3 problems files, entries, known, and edit. They also include toml patch, toml layout, ownership log/plans/commit/schema/installations, lifecycle apply, configuration-overrides, version-pin, and all of generation. Along the way it reads gspot.toml 5 times, validates it 3 times, builds the repository inventory twice, and writes ownership.json 5 to 8 times.

Proposal: `policy/file.ts` holds `readPolicyFile`, `writePolicyFile`, and `emitPolicy(previousText, policy)` (`review/code-commands/007`, `review/policy-format/007`). One `savePolicy(root, { change, summary, isDryRun })` in `commands/save-policy.ts` (`review/source-layout/005`) takes the write claim and reads the text once, applies `change` to the parsed table, formats it, and validates once. Validation also carries the reason rules and hints. On a dry run it returns the gspot.toml diff. Otherwise, it writes with compare-and-swap, opens one session from the new policy, and runs `writeOutputs`.

Each command keeps only its mutation, its summary, and its flags. `set` validates the setting name from the policy alone. Init and export call `emitPolicy`.

Files deleted: none whole. `commands/policy-edit.ts` and `types/commands/policy-edit.ts` become `commands/save-policy.ts` and `types/commands/save-policy.ts` (`review/source-layout/005`), which stay in `commands/` because they return a `CommandResult`. `prepareOverrides`, the `isReasonOwed` and `assertReason` of set.ts, and `isPathList` go.

Rough saving: 250 to 300 lines. One read, one validation, and one inventory per edit.

### 2. Ownership: one record per generated file, compare-and-swap writes, no journal

Today: `lifecycle/ownership/` holds 850 lines (log 179, plans 232, schema 133, commit 99, restoration 88, installations 76, claude-file 43). `lifecycle/merge` holds 217, and types plus config add about 140. Every identity carries a hash, a mode, and a link flag. Before writing, a batch is journaled as `pending` and recovered on the next open (`log.ts:14-27,65-94`; `commit.ts:41-62`; `schema.ts:91-130`). Installations are marked `installing`. Nine separate staleness checks sit on top of `replaceEntry`'s own compare-and-swap.

Records: `review/code-commands/005`, `006`, `019`, and `021`, and `review/commands-templates/005` (which removes the `export` kind), do the parts of this design that have a record. The journal removal and merging `commit.ts` into `plans.ts` have no record, so the target tree in `review/source-layout.md` keeps `commit.ts`.

Proposal: each record is `{path, kind: file|block|fields, hash}` plus the block or field originals. A generated file counts as edited when its current hash is neither the recorded hash nor the hash of the bytes about to be written. That second test makes an interrupted run safe without a journal.

Write files with `replaceEntry(expected)`, then save the state once per command. Drop mode from identity, because Git does not keep 0444 (`review/code-commands/019`). Drop the `export` kind and the `applyPlan` wrapper. Keep blocks, merged fields, restoration, adoption, the `CLAUDE.md` move, and the write claim. The write claim and atomic write in `platform/root/writes.ts` stay; the library table in `review/code-execution.md` covers `proper-lockfile`.

Files deleted: none whole. `lifecycle/ownership/commit.ts` shrinks into plans.ts.

Rough saving: 180 to 220 lines. State is written once per command instead of 5 to 8 times.

### 3. Manual configuration intent in gspot.toml, not hidden state (decided October 6, 2026)

Today: `selections` in `.gspot/state/ownership.json` records which language and framework configurations were added or removed by hand. Four functions in four files compute it, in a fixed order: `commands/configurations.ts:29-62`, `lifecycle/configuration-overrides.ts` (98 lines), `lifecycle/reconcile.ts:28-87`, and `init/prepare.ts:110`. `apply` uses it to decide what re-detection may add or remove in gspot.toml.

Proposal: `gspot remove` writes the configuration into a visible `removed_configurations = [...]` list (root or scope), and `gspot add` deletes it from that list. Re-detection then adds a detected configuration unless it is listed there. It never removes a listed configuration; when the evidence is gone, `doctor` suggests `gspot remove`. Nothing hidden needs recording.

Files deleted: `lifecycle/configuration-overrides.ts`. The `selections` schema field, `prepareOverrides`, `prepareConfigurationOverrides`, and the history half of `reconcileChoices` go too.

Rough saving: about 200 lines, and the intent becomes reviewable in Git.

### 4. Generation facts as data

Today: `generation/commitlint.ts` (41 lines) and `generation/stylelint.ts` (54) hand-code package.json redirects. `generation/vale-styles.ts:15-22` regex-templates YAML. Three glob escapers. ESLint level membership lives in the plugin, eslint-all-rules.json, and `generation/eslint/configuration.ts:117-149`. `TemplateInputs` copies `ScopeView` member by member. ESLint is special-cased by file suffix in `generation/fragments.ts:26,90`.

Proposal:

- Add a `redirect` flag on manifest `[[tool.replace]]` rows, with one generic emitter.
- Make the Vale styles Eta sources (`.eta`).
- Use one `literalGlob`.
- Have the plugin export `configs.all`, so the CLI adds only rule options.
- Spread `view` into the Eta inputs.
- Add a per-scope fragment flag on the manifest `[[tool_file]]` entry.

Files deleted: `generation/commitlint.ts` and `generation/stylelint.ts`, replaced by one file of about 40 lines.

Rough saving: about 150 lines.

### 5. One folder-swap install for npm, Python, and Vale

Today: `lifecycle/ownership/installations.ts:44-65` swaps the npm and Python folders with records and recovery. `tools/vale.ts:33-80` swaps the Vale packages with its own code and no record. `pruneInstallations` (`lifecycle/apply.ts:34-38`) deletes Vale packages outside the log. The install dry run keeps its own copy of the steps (`lifecycle/install.ts:48-227`; existing record main/007).

Proposal: add `vale` as an installation kind. Every phase returns the steps it will run, so the dry run and the run share one list.

Files deleted: none whole. The swap and removal code in `tools/vale.ts` goes.

Rough saving: 60 to 100 lines.

### 6. Read repository facts once per command

Today: `readManifests` runs 3+N times per `check`. Setting surfaces are built in `openSession`, again in `completenessProblems`, and again in `policyIndent`. `emitAll` runs twice per `install` and twice per `init`. Full re-detection runs on every `check`.

Proposal: `Session` carries `packageManifests` and the per-scope surfaces. Validation and generation take them from the session. Re-detection moves to `doctor` and `apply`.

Files deleted: none.

Rough saving: 30 to 60 lines, and much less repeated I/O on every hook run.
