# Internationalization

Internationalization (i18n) lets an application support different languages and regional formats.
A locale names the language and formatting conventions, message catalogs hold the translated text,
and ICU MessageFormat adds placeholders, plurals, and selection to messages.

## Locales and routing

- Define the supported locales, the default locale, and locale selection in one place, with BCP 47
  tags such as `en-GB`.
- Check a locale from a URL, cookie, or header against the supported list before loading messages,
  and build catalog import paths from checked values only. Unsupported input gets the documented
  default or not-found behavior, not a failed dynamic import.
- Choose the routing deliberately. A public site with locale-prefixed URLs needs locale-aware links,
  redirects, canonical URLs, alternate-language metadata, and sitemap entries. An application
  without indexed locale URLs can select the language by cookie or saved preference.
- Define the precedence among the URL, the saved preference, the negotiated header, and the
  default, without redirect loops.
- A request-local i18n configuration owns resolution, and request handling and displayed content
  use the same locale. Never keep a user's locale in mutable server module state, and partition
  localized data in server, browser, and CDN caches.

## Messages and catalogs

Keys name stable product concepts, so a reader finds the owning feature. Never build a key from an
arbitrary server string, a display name, or an English source sentence.

- Group related messages under one namespace per feature. Share a message only when its meaning
  and grammatical role match everywhere.
- Translators get complete sentences or clauses. Never concatenate translated fragments or
  pluralize by appending an English suffix; use ICU arguments, plurals, selects, and rich text
  through the library's rendering API.
- Placeholder names are part of the message contract, so a change to one updates every caller and
  catalog together.
- Rich tags stay stable and map to trusted components. Never accept executable markup from a
  translator or a provider response.
- Translate safe validation and error codes where they are presented. A raw schema exception, SQL
  message, or provider error is not a translation key.
- User-generated content, proper names, identifiers, and developer logs are interpolation data,
  not message keys, and stay untranslated.

Translate every application-authored string the user sees. That covers headings, buttons,
placeholders, toasts, validation errors, accessible names, image alternatives, navigation,
metadata, list status controls, and the empty, error, and loading states.

Catalogs agree on nested leaf keys, variable roles, and rich tags, and hold no empty strings. Every
message parses as ICU and includes the required fallback branches. Plural categories can differ by
locale, while every locale takes the same input value. Configure the catalog loader for the
application's format and namespace layout.

Translations land in the same change as their call sites; a locale that is not ready leaves the
supported list instead. Checks validate structure, not linguistic accuracy, so a review covers
hardcoded UI text, dynamic key resolution, and meaning, together with browser verification. Missing
keys are visible during development, and a production fallback is intentional and observable, never
a silent `catch` that hides a missing catalog.

## Rendering and formatting

- Use the framework's established i18n library. Translate on the server where rendering happens
  there, and give each client provider the scoped messages its interactive children need, never
  every locale or the whole catalog.
- Format numbers, currencies, dates, relative times, and time zones through locale-aware APIs.
  Never infer currency or time zone from language alone.
- Use an explicit product time-zone policy and one initial reference time on server and browser,
  so hydration matches. Define when relative timestamps refresh, without recreating a whole
  virtual list to update one label.
- Localized public routes get localized metadata, and each alternate link points to the matching
  resource in that locale, including a resource missing in some languages. Never generate an
  alternate URL that redirects forever or describes missing content.

## Changing the language

1. Keep the current resource, relevant search parameters, and hash where the routing supports them.
2. Persist the preference through the validated write owner when the product promises persistence.
3. Navigate through the locale-aware routing, so server-rendered content, client labels, and
   metadata agree.
4. Refresh locale-dependent query keys and results instead of keeping translated data under an
   identity without the locale.
5. Keep focus and scroll position sensible, and remeasure virtual rows after text metrics change,
   preserving the anchor.
6. Report a failed preference write; never show a completed selection that reverts on refresh.

A language menu names each language with a clear label, commonly its native name, not a flag.
Region and currency are separate choices when the product offers them.

## Right-to-left layout

Set the document's `lang` and `dir` for the selected locale, and test every supported right-to-left
(RTL) locale. Use logical spacing and alignment properties, and mirror an icon or image only when
its meaning requires it. Focus order and horizontal scrolling follow the direction, and record data
is never reversed to display RTL text. Test identifiers and URLs inside translated sentences, where
the directions mix.

## Verification

Verify the default locale and one other. Cover long translations and other writing systems in their
controls, plural cases, rich text, form failures, the selection after refresh, localized navigation,
and screen-reader labels. New locale support adds translator review, layout QA, and RTL testing
when the locale needs it.
