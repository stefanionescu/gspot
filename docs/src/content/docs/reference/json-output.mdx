---
title: JSON output
description: The JSON object that every gspot command prints under `--json`.
---

Add `--json` to any command to print its result as one JSON object on standard output. Progress messages still go to
standard error. You can run the command from any folder of your repository.

```shell
gspot check --json
```

## Fields of every object

| Field      | Meaning                                                                                  |
| ---------- | ---------------------------------------------------------------------------------------- |
| `version`  | The gspot version that ran, as a string.                                                 |
| `exitCode` | The process exit code. See [Exit codes](/reference/commands/#exit-codes).                |
| `notes`    | Lines of text for you to read, such as the next command to run. The list is often empty. |

The other fields depend on the command. A field has the same type in every command. For example, `written` always holds
a list of paths, and `summary` always holds a string.

## Command errors

When a command fails, its object also has `error` and `message`, and none of the fields of the command. `message`
describes the failure and what to do. For an unexpected failure, only `--verbose` adds `stack`, which holds the error
message and its stack trace. `error` holds one of these codes:

| Code            | What failed                                                                                                          |
| --------------- | -------------------------------------------------------------------------------------------------------------------- |
| `arguments`     | Command arguments or flags, or a command that does not fit the repository, such as `init` where `gspot.toml` exists. |
| `git`           | A Git operation.                                                                                                     |
| `copy`          | Copying the files of a check into a temporary folder.                                                                |
| `writing`       | Writing `gspot.toml` or a generated file.                                                                            |
| `filesystem`    | A repository file is missing, unreadable, or at a path that gspot rejects.                                           |
| `parse`         | A file has invalid syntax or structure, including malformed TOML in `gspot.toml`.                                    |
| `settings`      | A parsed setting has an invalid name, value, or combination.                                                         |
| `configuration` | A configuration that ships with gspot.                                                                               |
| `install`       | Installing tools.                                                                                                    |
| `tool`          | Finding or running a tool.                                                                                           |
| `runtime`       | The running Node.js or Bun version is older than the minimum of the package.                                         |
| `unexpected`    | An unexpected error. The message names it.                                                                           |
| `canceled`      | A signal stopped the command. `exitCode` holds the exit code of the signal.                                          |

## Generated files

`init`, `install`, and the commands that change settings list the generated files by what happened to them. Each field
holds paths relative to the root folder of the repository.

| Field       | Meaning                                                 |
| ----------- | ------------------------------------------------------- |
| `written`   | Files that gspot created or replaced.                   |
| `updated`   | Files where gspot changed only its own block or keys.   |
| `deleted`   | Files that gspot deleted because no setting needs them. |
| `unchanged` | Files that already matched `gspot.toml`.                |

## `gspot scan`

| Field           | Meaning                                                                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `totals`        | The counts of the run: `files`, `checks`, `findings`, `filesFlagged`, and `seconds`.                                                |
| `categories`    | The findings by category, real problems first: `name`, `count`, the five largest `rules`, and three `examples` of the largest rule. |
| `filesToFormat` | Number of files that differ from your style.                                                                                        |
| `notRun`        | One line for each check that could not run.                                                                                         |
| `leftOut`       | The checks that a scan leaves out, because they run your code.                                                                      |
| `cost`          | The tools, the megabytes in `.gspot/`, and the seconds in `perTool`.                                                                |
| `plan`          | The plan that `gspot init` prints.                                                                                                  |
| `settingsText`  | The text of the `gspot.toml` that init writes.                                                                                      |
| `nextSteps`     | The commands to run next.                                                                                                           |
| `checks`        | The result of every planned check, as in [`gspot check`](#gspot-check), with every finding.                                         |

## `gspot baseline`

| Field          | Meaning                                                                     |
| -------------- | --------------------------------------------------------------------------- |
| `summary`      | One sentence about the result.                                              |
| `findingCount` | Number of findings that `gspot.baseline.json` holds.                        |
| `fileCount`    | Number of files that those findings sit in.                                 |
| `leftOut`      | The checks that keep failing, because a baseline leaves their findings out. |

## `gspot init`

The object of `gspot init --json` also has the [generated-file fields](#generated-files).

| Field          | Meaning                                                                  |
| -------------- | ------------------------------------------------------------------------ |
| `root`         | The repository folder.                                                   |
| `plan`         | The plan that `init` prints.                                             |
| `settingsText` | The text of the new `gspot.toml`.                                        |
| `installed`    | One line per install step that changed something, as in `gspot install`. |
| `missing`      | What stays missing after the install, with what to do about it.          |
| `steps`        | The commands that the install ran, as argument lists.                    |

| Field of `plan`                                         | Holds                                                                                                                                      |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `level`                                                 | The level.                                                                                                                                 |
| `configurations`                                        | One item per configuration: `configuration`, `origin`, `scopes`, `checks`, and `checksOff`.                                                |
| `write`, `deleted`, `keep`, `change`, and `lintFolders` | One row per file: `path` and `note`.                                                                                                       |
| `lintCommands`                                          | One row per command: `file`, `line`, `source`, `command`, `tool`, and `fix`.                                                               |
| `carryover`                                             | One row per replaced tool config: `path`, `tool`, `covered`, `carried`, `differing`, `reasons`, `plugins`, `commandChecks`, and `dropped`. |
| `from`                                                  | With `--from`: the `file` that `--from` names, and the `leftOutSettings`.                                                                  |

## `gspot install`

The object of `gspot install --json` also has the [generated-file fields](#generated-files).

| Field       | Meaning                                                          |
| ----------- | ---------------------------------------------------------------- |
| `summary`   | One sentence about the result.                                   |
| `installed` | One line per step that changed something, such as the npm tools. |
| `missing`   | What stays missing, with what to do about it.                    |
| `steps`     | The commands that install ran, as argument lists.                |

`notes` holds what you still have to do, such as the lines to add to hooks that another tool manages.

## `gspot check`

`gspot check --json` returns the report of the run. `exitCode` says whether the checks passed.

To see how the generated files differ from `gspot.toml` without writing them, run
`gspot check --only gspot/generated-files --verbose --json`. The finding of a changed file includes `diff`, a unified
diff of the generated content or of the gspot block. When only the file mode changed, the finding shows the old and the
new mode. Without `--verbose`, gspot does not compute these diffs.

| Field             | Meaning                                                                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `stages`          | The stages that ran, such as `commit` and `push`.                                                                               |
| `started`         | Start time as an ISO 8601 timestamp.                                                                                            |
| `duration`        | Elapsed run time in milliseconds.                                                                                               |
| `comparison`      | When present, the content that the run read, `working-tree`, `index`, or `commit`, and its reference.                           |
| `checks`          | The result of each planned check, with its findings. A check that no file selects appears only with `--verbose`.                |
| `skippedCount`    | The number of skipped checks for each `cause`, the checks that no file selects included.                                        |
| `ignores`         | Ignores in effect, with their check, optional lint rule, paths, and reason.                                                     |
| `baselined`       | The number of findings that `gspot.baseline.json` removed, for each check.                                                      |
| `unstagedChanges` | The number of changed files that the run left out because it read only the staged files.                                        |
| `partial`         | Whether the run selected only staged files, changed files, or named paths.                                                      |
| `fixes`           | When present, the changed files, files restored after broken fixes, files skipped for merge-conflict markers, and fixer errors. |
| `failed`          | Check IDs that failed or stopped with an error, and the checks whose fixer failed.                                              |

Each item of `checks` has `check`, `scope`, `status`, `fileCount`, `duration`, and `findings`. It can also have these
fields: `help`, which says how to fix its findings; `fixCommand`, the `gspot check --fix` command that fixes them;
`files`; `note`; `rerun`; `command`; and `cause`, for a skipped check. With `--verbose`, a check that stopped with an
internal error also has `stack`, which holds the error message and its stack trace.

`status` holds `passed`, `failed`, `missing`, `error`, `canceled`, or `skipped`. `missing` and `error` mean that the
run did not finish, and it exits with code `2`. `canceled` marks a check that a signal stopped, and the run then exits
with the code of that signal. `cause` holds `system`, `replaced`, `setting`, `condition`, `level`, `ignore`, or `no-files`.

Each finding has `check`, `file`, `message`, `fixable`, and `explain`. The `explain` field holds the command that
explains its check or lint rule. A finding can also have `line`, `column`, `rule`, and `help`. Its `help` appears only
when it differs from the `help` of its check. Lines and columns count from `1`. A finding without a place in a file can
have an empty `file`.

`gspot check --hook pre-push --json` checks the tree of each pushed commit. It returns these fields:

- `revisions`: one item for each tree, with `hash`, `refs`, `commits`, `shallow`, and its `report`.
- `skipped`: the pushed refs that gspot did not check, with `ref`, `hash`, and `reason`.
- `canceled.pendingRefs`: present when a signal stopped the run.

## Commands that change settings

`add`, `remove`, `set`, `unset`, `ignore`, and `unignore` return these fields. When the command writes `gspot.toml` or
a generated file, the object also has the [generated-file fields](#generated-files). When an edit leaves `gspot.toml`
and every generated file unchanged, the object has no generated-file fields.

| Field     | Meaning                                   |
| --------- | ----------------------------------------- |
| `changed` | Whether the command changed `gspot.toml`. |
| `summary` | One sentence about the result.            |

Do not read `changed` as a sign that the generated files changed. A command that leaves `gspot.toml` unchanged can
still rewrite generated files that are out of date.

## `gspot list`

`gspot list --json` and `gspot list configurations --json` return these fields.

| Field       | Meaning                                                             |
| ----------- | ------------------------------------------------------------------- |
| `selected`  | Each selected configuration, with `name` and `checks`.              |
| `removed`   | Each removed configuration, with `name`, `scope`, and its `reason`. |
| `available` | Each configuration that you can add, with `name` and `description`. |

Each item of `checks` has `check`, `scope`, and `status`: `on`, or `skipped` with a `cause`, as in
[`gspot check`](#gspot-check).

## `gspot list settings`

| Field      | Meaning                     |
| ---------- | --------------------------- |
| `settings` | Each setting of each scope. |

Each item has `setting`, `source`, and `scope`. It also has `value` when a default or `gspot.toml` gives one. `source`
has a `kind` and a `name` that say where the value comes from: `default` and `gspot`, `configuration` and its name,
`root` and `gspot.toml`, `scope` and the path of the scope that sets it, or `unset`. When a change of the setting needs
a reason, `reasonFor` names that change, such as `raising`.

## `gspot explain`

`gspot explain <subject> [rule] --json` returns `kind`, `subject`, and the fields of that kind. To explain a lint rule,
put its name after its check, such as `gspot explain javascript/eslint no-console --json`.

### `check`

| Field           | Meaning                                                                        |
| --------------- | ------------------------------------------------------------------------------ |
| `check`         | The check ID.                                                                  |
| `configuration` | When present, the configuration of a shipped check.                            |
| `command`       | When present, the command of a `[[command_check]]`.                            |
| `paths`         | When present, the paths of a `[[command_check]]`.                              |
| `stage`         | The stage that runs the check.                                                 |
| `level`         | The level that turns the check on.                                             |
| `summary`       | What the check looks for.                                                      |
| `why`           | Why it matters.                                                                |
| `help`          | How to fix a finding.                                                          |
| `condition`     | When present, what must hold for the check to run.                             |
| `crashPattern`  | When present, the output that marks a crash of the tool.                       |
| `runInCopy`     | When present, whether the check runs on a copy of the files.                   |
| `minVersions`   | The oldest version of each runtime or tool that the check needs.               |
| `turnOff`       | The `gspot ignore` command for some paths, and for one lint rule when present. |
| `settingNames`  | The settings that change the check.                                            |
| `ruleFiles`     | The rule files that describe what the check enforces.                          |
| `selected`      | When present, whether a scope selects the configuration of the check.          |
| `ignores`       | The ignores of `gspot.toml` that name the check, with `reason` and `command`.  |

### `lint-rule`

| Field           | Meaning                                                                      |
| --------------- | ---------------------------------------------------------------------------- |
| `tool`          | When present, the tool that reports the rule.                                |
| `rule`          | The rule ID.                                                                 |
| `check`         | The check that runs the rule.                                                |
| `page`          | The rule's documentation link, or `null`.                                    |
| `description`   | The rule's description, or `null`.                                           |
| `why`           | When present, why the rule matters.                                          |
| `fix`           | When present, how to fix a finding.                                          |
| `example`       | When present, an example.                                                    |
| `explanation`   | When present, the full explanation, which needs `--verbose`.                 |
| `turnOff`       | The `gspot ignore` commands for the rule, `everywhere` and for some `paths`. |
| `changeOptions` | When present, the `gspot set` command that changes the options of the rule.  |

### `configuration`

| Field            | Meaning                                                                        |
| ---------------- | ------------------------------------------------------------------------------ |
| `name`           | The configuration name.                                                        |
| `group`          | Its group.                                                                     |
| `title`          | Its title.                                                                     |
| `description`    | What it covers.                                                                |
| `requires`       | The configurations that it needs.                                              |
| `tools`          | Its tools and their versions.                                                  |
| `checks`         | Its checks, each with `check` and `stage`.                                     |
| `settingNames`   | Its settings.                                                                  |
| `ruleFiles`      | Its rule files in your repository.                                             |
| `alwaysSelected` | Whether gspot selects it in every repository.                                  |
| `removed`        | Each scope that removes it, with `scope`, `reason`, and the `command` to undo. |

### `setting`

| Field              | Meaning                                                                                                                       |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `setting`          | The setting name.                                                                                                             |
| `type`             | Its type.                                                                                                                     |
| `description`      | What it does.                                                                                                                 |
| `default`          | When present, its default.                                                                                                    |
| `defaultAll`       | When present, its default at level `all`.                                                                                     |
| `languageDefaults` | When present, its default per language.                                                                                       |
| `reasonFor`        | When present, the change that needs a reason.                                                                                 |
| `scopes`           | Each scope, with `scope`, `default`, `value`, `source` as in `gspot list settings`, and, when present, `readBy` and `reason`. |

### `path`

| Field            | Meaning                                    |
| ---------------- | ------------------------------------------ |
| `path`           | The path from the root of the repository.  |
| `scope`          | Its scope.                                 |
| `fileKind`       | Its kind, such as `source`.                |
| `fileKindOrigin` | When present, what set the kind.           |
| `tags`           | Its tags.                                  |
| `configurations` | The selected configurations that check it. |
| `checks`         | The checks that read it.                   |
| `ignores`        | The ignores that cover it.                 |
| `unchecked`      | When present, why no check reads it.       |
| `remedy`         | When present, what to do about it.         |

## `gspot doctor`

`gspot doctor --json` returns the state of the setup. `exitCode` holds `1` when a tool, an environment, or a
hook needs you to act.

| Field           | Meaning                                                                                         |
| --------------- | ----------------------------------------------------------------------------------------------- |
| `tools`         | Each tool with `name`, `kind`, and `state`, and `want`, `found`, `path`, and `help` when known. |
| `environments`  | Project environments that a check needs and that are missing.                                   |
| `suggestions`   | Configurations to add, and files that no configuration checks.                                  |
| `hooks`         | The state of the Git hooks.                                                                     |
| `ci`            | The state of the CI workflow.                                                                   |
| `ruleFileCount` | The number of rule files for coding agents.                                                     |
| `submodules`    | Submodule paths, whose contents gspot does not read.                                            |

`hooks` has `ready`. When gspot knows them, it also has `tool`, the program that runs the hooks, and `lines`, what to
do about them. `ci` has `enabled`, and when gspot knows them, `provider` and the workflow `file`.
