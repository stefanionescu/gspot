Start with `gspot doctor`, which lists missing tools, problems with the Git hooks, and a gspot version other than the
one that your repository pins. `gspot check --only gspot/generated-files --verbose` lists each generated file that does
not match `gspot.toml`, with its diff. When you [report a problem](https://github.com/stefanionescu/gspot/issues),
include the output, the check ID, and a command that shows the problem, and leave out credentials.

## A command reports an error in `gspot.toml`

A key that gspot cannot read stops every command that reads the file, `gspot explain` and `gspot list settings` too. The
message names the key and what it accepts, so fix the line by hand.

## A commit or push fails on findings from before gspot

A commit checks the files that you stage, so it also reports the old findings of each file that it touches. The first
push runs the checks that read the whole project, such as `typescript/tsc`, which report every old finding. Fix or
ignore each finding, as [Clean up the first findings](/start/quickstart/#clean-up-the-first-findings) shows.

## A check reports `missing`

Run `gspot install`. Without mise, install the tools that `gspot doctor` lists yourself, as
[What you need](/start/install/#what-you-need) describes. While a tool is missing, the run exits with code 2, and in a
Git hook, that also stops the commit.

## A lockfile in `.gspot/` has a merge conflict

Delete the lockfiles in `.gspot/`, run `gspot install`, and commit the new lockfiles.

## `gspot install` or `gspot scan` hits the GitHub rate limit

mise looks up each pinned tool on GitHub. Without a token, GitHub allows 60 lookups an hour, and gspot prints:

```text
GitHub limits the release lookups of mise without a token. Set GITHUB_TOKEN to a GitHub token, then run gspot install again.
```

Set `GITHUB_TOKEN` to a GitHub token that can read public releases, then run the command again. `gspot scan` stops with
exit code 2 when it hits the same limit.
[mise: If something does not work](https://mise.jdx.dev/getting-started.html#if-something-doesn-t-work) has more help.

## A generated file has local edits

`gspot install` overwrites the local edits in a generated file, so move each change into `gspot.toml` first, as
[Do not edit generated files](/reference/generated-files/#do-not-edit-generated-files) describes.

## A check runs slowly

Run `gspot check --verbose`, and each passed check shows its number of files, its time, and the command that it ran. To
time one check alone, run `gspot check --only <check>`. A tool command that runs longer than `tool_timeout_seconds`, 600
seconds by default, stops with an error.

## Your package manager cannot find gspot

Each new clone or Git worktree needs its own install, because it cannot use the packages of another worktree. Run the
install command of your package manager, then `gspot install`. With mise, run `mise install`, then `gspot install`.

## A hook cannot find Node.js, Yarn, or mise

Hooks in npm, pnpm, and Bun repositories need `node`, and those in Yarn and mise repositories need `yarn` or `mise`. The
message names the program and the `PATH` that the Git client gave the hook:

A Git client in an editor can get a different `PATH` from your terminal. Start the client from a terminal, or add the
folder of the program to the `PATH` of the client, then restart the client.

When the hook says that gspot is not installed in the worktree, run the install command that the hook prints in that
worktree, then `gspot install`. With mise, run `mise install` in that worktree, then `gspot install`.
