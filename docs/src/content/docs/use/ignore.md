---
title: Ignore findings
description: Ignore a check or a lint rule for some files, with a reason that gspot records.
---

An ignore turns off a check, or one lint rule of a check. It covers every file or only some paths. gspot saves the
ignore in `gspot.toml` with the reason that you give. Fix the code first. Add an ignore only when you can say why the rule does
not fit your code. A suppression is an inline comment that turns off a lint rule, such as `// eslint-disable-next-line`.

## Ignore a lint rule

```shell
gspot ignore javascript/eslint --rule no-console --paths "scripts/**" --reason "Scripts print their results to the terminal."
```

- Leave out `--rule` to ignore the whole check.
- Leave out `--paths` to cover every file.
- Write a reason of two or more words.

gspot rejects a rule name that the tool does not know. For a check that takes no `--rule`, give `--paths` instead.

To raise a size or complexity limit instead, follow [limits](/reference/gspot-toml/#limits).

## Choose the paths

`--paths` takes a file, a folder, or a glob pattern, relative to your current folder. gspot saves it relative to the
root folder of the repository. Each path must match at least one file. To give more paths, repeat `--paths`, as in
`--paths "scripts/**" --paths "fixtures/**"`. A comma does not separate paths: it stays part of the path.

## Ignore a dependency advisory

To ignore one security advisory of a dependency, give the advisory ID as the rule:

```shell
gspot ignore dependencies/osv-scanner --rule <advisory-id> --reason "<why>"
```

## Ignore files in every check

gspot reads the files that Git tracks, and the untracked files that `.gitignore` does not exclude. Most checks skip
these files:

- generated files, which start with a comment such as `@generated` or `// Code generated by ... DO NOT EDIT.`
- vendored files, which are copies of code from other projects: license files, and files in a folder named `vendor`,
  `third_party`, `third-party`, `node_modules`, `Pods`, `Carthage`, or `.build`
- binary files

Secret scans still read every file, and dependency checks still read lockfiles.

To skip other generated or vendored files, mark them in `.gitattributes`. GitHub reads these marks too:

```text title=".gitattributes"
src/api/schema.ts linguist-generated
lib/upstream/** linguist-vendored
```

To skip any other files in every check, add an ignore without a check ID:

```shell
gspot ignore --paths "fixtures/**" --reason "Fixtures copy upstream files byte for byte."
```

A path that starts with `!` puts a file back into the check, but only for Prettier, typos, and ESLint. The other tools
skip such a path.

To see which checks read a file and which ignores cover it, run `gspot explain ./<path>`.

## Remove an ignore

```shell
gspot unignore javascript/eslint --rule no-console --paths "scripts/**"
```

When you delete the files that an ignore covers, remove the whole ignore: run `gspot unignore` without `--paths`.

`gspot check --verbose` lists each ignore that applies, with its reason.

## Changes that weaken the checks

The check `gspot/weakenings` runs before each push and in CI. It compares `gspot.toml` and `gspot.baseline.json` with
their versions at the base revision. Before a push, the base is where the pushed commits start. In CI, the base is the
revision that `--base` names. `gspot check` without options compares the two files with the last commit. The check
lists each change that makes the checks less strict:

- a new ignore, or an ignore that covers more
- a removed configuration
- a lower level
- a weaker setting, such as a raised limit
- the Git hooks or the rule files turned off
- a baseline count that goes up

A change with a reason shows as a note. A change without a reason fails the check. The first baseline that you record
also shows as a note.

Ignores, removed configurations, and settings each store their own reason. A lower level, the hooks, the rule files,
and a baseline have no reason field. For these, give the reason with an ignore of the matching rule of
`gspot/weakenings`:

```shell
gspot ignore gspot/weakenings --rule level --reason "The team moves to level all after the release."
```

The rules are `level`, `hooks`, `rule-files`, and `baseline`. gspot rejects an ignore of the whole check.
