---
title: Ignore findings
description: Ignore a check or a lint rule for some files, with a reason that gspot records.
---

An ignore turns off a check or one of its lint rules, for every file or for some paths. gspot records it in
`gspot.toml` with your reason. Fix the code first. Ignore a finding only when you can say why the rule does not fit.

## Ignore a lint rule

```shell
gspot ignore javascript/eslint --rule no-console --paths "scripts/**" --reason "Scripts print their results to the terminal."
```

- Leave out `--rule` to ignore the whole check.
- Leave out `--paths` to cover every file.
- Write a reason of two or more words.

gspot refuses a rule that the tool does not know. When a check takes no `--rule`, give `--paths` instead.

To raise a size or complexity limit instead, see [limits](/reference/gspot-toml/#limits).

## Choose the paths

`--paths` takes a file, a folder, or a glob, from your current folder. gspot saves it relative to the repository root.
Each path must match a file in the repository. Repeat `--paths` for more paths:
`--paths "scripts/**" --paths "fixtures/**"`. A comma stays part of the path.

## Ignore a dependency advisory

Give the advisory ID as the rule:

```shell
gspot ignore dependencies/osv-scanner --rule <advisory-id> --reason "<why>"
```

## Ignore files in every check

gspot reads the files that Git tracks, and untracked files that `.gitignore` does not hide. It leaves these out of
most checks:

- generator output, which starts with a banner such as `@generated` or `// Code generated by ... DO NOT EDIT.`
- vendored files: license files, and files in a folder named `vendor`, `third_party`, `third-party`, `node_modules`,
  `Pods`, `Carthage`, or `.build`
- binary files

Secret scans still read every file, and dependency checks still read lockfiles.

Mark other generator output and vendored files in `.gitattributes`. GitHub reads these marks too:

```text title=".gitattributes"
src/api/schema.ts linguist-generated
lib/upstream/** linguist-vendored
```

For any other file, leave out the check:

```shell
gspot ignore --paths "fixtures/**" --reason "Fixtures copy upstream files byte for byte."
```

A path that starts with `!` keeps a file in the check for Prettier, typos, and ESLint. The other tools skip such a
path.

Run `gspot explain ./<path>` to see which checks read a file and which ignores cover it.

## Remove an ignore

```shell
gspot unignore javascript/eslint --rule no-console --paths "scripts/**"
```

After you delete an ignored file, remove the whole ignore: leave out `--paths`.

`gspot check --verbose` lists each ignore in effect, with its reason.

## Changes that weaken the checks

`gspot/weakenings` runs before each push and in CI. It compares `gspot.toml` and `gspot.baseline.json` with the base
revision: the pushed range, or `--base` in CI. A plain `gspot check` compares them with the last commit. The check
lists each change that weakens the checks:

- an added or wider ignore
- a removed configuration
- a lower level
- a looser setting, such as a raised limit
- hooks or rule files turned off
- a baseline that gains a count

A change with a reason prints as a note. A change with no reason fails the check. The first baseline prints as a note.

Ignores, removed configurations, and settings hold their own reason. A lower level, hooks, rule files, and a baseline
have no reason field. Give the reason through an ignore of that rule:

```shell
gspot ignore gspot/weakenings --rule level --reason "The team moves to level all after the release."
```

Use one of these rules: `level`, `hooks`, `rule-files`, or `baseline`. gspot refuses an ignore of the whole check.
