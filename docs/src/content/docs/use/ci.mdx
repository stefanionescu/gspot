gspot can write one CI job that runs the checks on pull requests and on pushes to the default branch. It writes one
workflow file and leaves your other workflows alone. CI stays off until you turn it on.

## Turn CI on

For GitHub:

```shell
gspot set ci.enabled true
```

gspot writes `.github/workflows/gspot.yml`. Commit it.

For GitLab, also set the provider:

```shell
gspot set ci.provider gitlab
```

gspot writes `.gitlab/ci/gspot.yml`. Include it from `.gitlab-ci.yml`:

```yaml
include:
  - local: .gitlab/ci/gspot.yml
```

`gspot doctor` prints these commands when it finds GitHub or GitLab CI files, or an `origin` remote on either.

## What the job checks

On GitHub, the workflow has one job, `lint`. It runs for pull requests, merge queues, and pushes to the default branch.
A push to another branch skips the job, so open a pull request to check a branch.

When the repository selects a testing configuration such as `jest`, `vitest`, or `pytest`, the workflow adds a `tests`
job with the same steps, so the lint result does not wait for your test suite. `lint` leaves out the coverage checks
with `--skip`, and `tests` runs them with `--only`. On GitLab, one job runs both. To run your tests only in your own
workflow, leave those configurations out.

The job checks the files changed after the pull or merge request base, or after the previous push. The first push of a
branch checks every file. Manual checks run only when you name them with `--only`, so the job does not run them.

The job fails when `gspot install` changes a file, such as a generated file that someone edited by hand, or a missing
or stale lockfile. Run `gspot install` on your machine and commit the changed files.

## Run on more systems

On GitHub, the job runs on Linux. When the repository selects the `swift` configuration, the workflow also runs on
macOS. To add other systems:

```shell
gspot set ci.operating_systems linux macos windows
```

With more than one system, each system gets its own job: `lint-linux`, `lint-macos`, and `lint-windows`. A `tests` job
follows the same names: `tests-linux`, `tests-macos`, and `tests-windows`. Pick only systems where your checks can run.

To run the Linux job on a larger or self-hosted runner, name its label:

```shell
gspot set ci.linux_runner ubuntu-24.04-8core
```

Both settings work on GitHub only; gspot refuses them with `ci.provider = "gitlab"`.

## Install and cache steps

Each GitHub job installs mise and the pinned gspot version once. It adds the installed tools to `PATH`, then uses that
gspot for the tool install and the checks. It gives mise the job token as `MISE_GITHUB_TOKEN`.

The GitLab job runs in the `ghcr.io/jdx/mise` image at the pinned mise version, on the runners of GitLab. It keeps its
mise folders under the project folder, so GitLab caches them, with a cache key from the mise files in `.gspot/`.

The GitLab job runs in the `.pre` stage, and only in merge request pipelines and pipelines of the default branch. GitLab
runs `.pre` only when a pipeline also has a job in another stage. To run one pipeline for each merge request, add this
block to your `.gitlab-ci.yml`:

```yaml
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

Before `gspot install`, the GitHub job installs the locked dependencies of the root and of each scope, so the checks
that read them find them:

Each command fails on a lockfile that does not match its project. In a Next.js scope, the step then runs
`next typegen`, so the typed lint rules find the route types.

To run your own command instead, set it. The job runs it before `gspot install` and stops if it fails:

```shell
gspot set ci.setup_command -- bun install --frozen-lockfile
```

gspot quotes each argument, so spaces, quotes, and `$` reach the command as plain text.

## Use your own pipeline

Use your own pipeline on another CI provider, when your project installs private packages, or when its tests need a
database or another service. The generated job passes no secret to the install step and starts no service container.
Keep `ci.enabled` off in that case.

Clone with the full history, so that gspot can compare with the base revision. Install mise and the runtime of your
project, and set `GITHUB_TOKEN` for the release lookups of mise. Then run these steps, started the way your repository
starts gspot; see [Install](/start/install/#add-gspot). With Bun:

```shell title="example"
bun install --frozen-lockfile
bunx --no-install gspot install
git add --intent-to-add -- .
git diff --exit-code
bunx --no-install gspot check --base "$BASE"
```

`git diff --exit-code` fails when `gspot install` changed a file, such as a stale lockfile in `.gspot/`. `$BASE` names
the revision to compare with, so the check reads only the changed files:

| Provider                                                                                         | `BASE`                                                  |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| [Bitbucket Pipelines](https://support.atlassian.com/bitbucket-cloud/docs/variables-and-secrets/) | `$BITBUCKET_PR_DESTINATION_COMMIT`                      |
| [Azure Pipelines](https://learn.microsoft.com/en-us/azure/devops/pipelines/build/variables)      | `origin/${SYSTEM_PULLREQUEST_TARGETBRANCH#refs/heads/}` |
| [Jenkins](https://www.jenkins.io/doc/book/pipeline/multibranch/)                                 | `origin/$CHANGE_TARGET`                                 |
| Any other provider, such as CircleCI                                                             | `$(git merge-base origin/<default-branch> HEAD)`        |

An empty `BASE` checks every file. In a CI clone, `--changed` compares the branch with its own copy on the remote and
checks nothing, so give `--base`. In a shallow clone, gspot cannot find the base revision and says so.

Let the pipeline fail on the gspot exit code: `1` means findings, and `2` means the run did not finish. A missing tool
gives exit code 2, and the report names it. `gspot check --json` prints the report as JSON.

Do not cache or upload credentials. To cache downloads and installed tools, key the cache on the gspot version, the
files in `.gspot/` that pin the tools, and your lockfiles.

## Run gspot in a container

`.gspot/node_modules/` and `.gspot/.venv/` hold tools built for one system. When a dev container shares the checkout
with the host, an install in the container replaces the tools of the host, and the host then reports errors until it
runs `gspot install` again. Mount `.gspot/node_modules/` and `.gspot/.venv/` as volumes of the container, and run
`gspot install` in its `postCreateCommand`.

## Turn CI off

Run `gspot set ci.enabled false`. gspot deletes the workflow file.
