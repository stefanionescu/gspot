gspot writes one workflow file and never touches the others. Keep your tests, builds, and deploys in your own workflow
files; GitHub runs every workflow file in parallel, so they never wait on gspot. On GitHub, a testing configuration such
as `jest` or `pytest` runs its tests in a separate `tests` job. On GitLab, it runs them inside the gspot job. To run your
tests only in your own workflow, leave those configurations out.

`gspot init` leaves CI off and keeps your existing workflows. Run `gspot doctor` to see the commands that enable CI
for your provider. It detects GitHub or GitLab from your CI files or the `origin` remote.

If an existing pipeline already runs gspot, keep CI off and use that pipeline.

## Turn CI on

To turn CI on later, run the first command. For GitLab, run the second one too:

```shell
gspot set ci.enabled true
gspot set ci.provider gitlab
```

`gspot set` writes the workflow file. For GitHub, gspot writes `.github/workflows/gspot.yml`. For GitLab, it writes
`.gitlab/ci/gspot.yml`. Include that file in your pipeline:

```yaml
include:
  - local: .gitlab/ci/gspot.yml
```

## What the job checks

On GitHub, the workflow has one job, `lint`. It runs for pull requests, merge queues, and pushes to the default branch.
A push to another branch skips the job, so open a pull request to check a branch.

When the repository selects a testing configuration such as `jest`, `vitest`, or `pytest`, the workflow adds a `tests`
job with the same steps, so the lint result does not wait for your test suite. `lint` leaves out the coverage checks
with `--skip`, and `tests` runs them with `--only`. The GitLab include keeps one job.

The job checks the files changed after the pull or merge request base, or after the previous push. The first push of a
branch checks every file. Manual checks run only when you name them with `--only`; the generated workflow does not
run them automatically.

The job fails when `gspot install` changes a file in `.gspot/`. This includes missing and stale lockfiles.
Run `gspot install` on your machine and commit the changed files.

## Systems

On GitHub, the job runs on Linux. When the repository selects the `swift` configuration, the workflow also runs on
macOS. To add other systems:

```shell
gspot set ci.operating_systems linux macos windows
```

With more than one system, each system gets its own job: `lint-linux`, `lint-macos`, and `lint-windows`. A `tests` job
follows the same names: `tests-linux`, `tests-macos`, and `tests-windows`. Pick only systems where your checks can run.

To run the Linux job on a larger or self-hosted runner, name its label:

```shell
gspot set ci.linux_runner ubuntu-24.04-8core
```

Both settings work on GitHub only; gspot refuses them with `ci.provider = "gitlab"`.

## Install steps

Each GitHub job installs mise and the pinned gspot version once. It adds the installed programs to `PATH`, then uses
that gspot executable for tool installation and checks. The GitLab job runs in the `ghcr.io/jdx/mise` image at the
pinned mise version, on GitLab's own runners. It keeps its mise folders under the project folder, so GitLab can cache
them, with a cache key from the `.gspot` lockfiles.

The GitLab job runs in the `.pre` stage, and only in merge request pipelines and pipelines of the default branch. GitLab
runs `.pre` only when a pipeline also has a job in another stage. To run one pipeline for each merge request, add this
block to your `.gitlab-ci.yml`:

```yaml
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

Before `gspot install`, the GitHub job installs the locked dependencies of the root and of each scope, so the checks
that read them find them:

Each command fails on a lockfile that does not match its project. In a Next.js scope, the step then runs
`next typegen`, so the typed lint rules find the route types.

To run your own command instead, set it. The job runs it before `gspot install` and stops if it fails:

```shell
gspot set ci.setup_command -- bun install --frozen-lockfile
```

gspot quotes each argument, so spaces, quotes, and `$` reach the command as plain text.

The gspot installation step gives mise the job token as `MISE_GITHUB_TOKEN`; `gspot install` downloads the exact URLs of
the mise lockfile under `.gspot/`. In other pipelines, set `MISE_GITHUB_TOKEN` yourself.

## Your own pipeline

Use your own pipeline when your project installs private packages, or when its tests need a database or another
service. The generated job passes no secret to the install step and starts no service container. Keep `ci.enabled` off
in that case.

Install mise and the runtime of your project. Then install your dependencies and run gspot the way your repository
starts it; see [Installation](/start/install/#choose-how-to-install). With Bun:

```shell
bun install --frozen-lockfile
bunx --no-install gspot install
bunx --no-install gspot check
```

With mise:

```shell
mise exec -- gspot install
mise exec -- gspot check
```

Let the pipeline fail on the gspot exit code: `1` means findings, and `2` means the run did not finish. A missing
program gives exit 2, and the report names it. `gspot check --json` prints the report as JSON.

Do not cache or upload credentials. To cache downloads and installed tools, key the cache on the gspot
version, the files in `.gspot/` that pin the tools, and your lockfiles.

## Turn CI off

Run `gspot set ci.enabled false`. gspot deletes the workflow file.
