Commit your work first, so that you can go back. The [releases page](https://github.com/stefanionescu/gspot/releases)
lists the gspot versions, and the [changelog](/reference/changelog/) says what each one changes. Put the version that you
want in place of `<version>`:

<Tabs syncKey="package-manager">
    {setup.map(({ label, start, add }) => (
        <TabItem label={label}>
            <Code lang="shell" code={[`${add}@<version>`, `${start} install`, `${start} check`].join('\n')} />
        </TabItem>
    ))}
</Tabs>

`gspot install` writes the generated files again and installs the tool versions of the new release. If it rejects a
setting in `gspot.toml`, the message names the line and what to write instead. If it says
`gspot did not overwrite these files`, the new release writes a file where you have one of your own, so move yours out of
the way and run it again.

It also stops and names the tool if a pinned tool is newer than `dependencies.min_release_age_days`, 7 by default, so wait
or lower the setting. A clone that installs from the committed tool lockfiles does not wait.

A new release can pin tools that format or report code in a new way, and `gspot check` lists what they find in the whole
repository. If your repository had no findings before the upgrade, run `gspot check --fix`, then fix or ignore the rest.
If it still has old findings, leave them, because a commit checks what you stage, and fix each file as you touch it.

Commit these files together: the generated files that changed, in `.gspot/` and outside it, `gspot.toml` if you changed
it, and either `package.json` with its lockfile or `mise.toml`. The next push runs the push checks with the new tools,
and `gspot check --only push` shows the result first. Then run `gspot install` in each other clone, as
[Set up a clone](/start/install/#set-up-a-clone) describes.

To go back, check out the commit from before the upgrade. An upgrade can leave older tool versions and download caches
outside your repository, and [Free disk space](/reference/generated-files/#free-disk-space) shows how to delete them.

## Upgrade from 0.3.9

This release removes commands, flags, and settings, so a repository on 0.3.9 also follows these steps. The
[changelog](/reference/changelog/) lists every change.

1. Replace the old flags in your scripts and CI steps. `gspot check --stage <stage>` becomes
   `gspot check --only <stage>`, and `gspot check --changed` becomes `gspot check --base origin/HEAD`.
2. Delete `gspot.baseline.json` and each `[[ignore]]` of `gspot/baseline`. Its old findings come back in the files that
   you touch and at the next push, so follow
   [Clean up the first findings](/start/quickstart/#clean-up-the-first-findings).
3. Run the commands above. `gspot install` stops on each setting that this release refuses, such as
   `limits.min_function_statements`, and its message names the fix. It also writes new Git hooks, because a hook from
   0.3.9 stops on its old flag.
4. Drop the group folder from each path that you wrote by hand, such as in an editor setting or a CI script.
   `.gspot/configurations/<group>/<configuration>/` becomes `.gspot/configurations/<configuration>/`.
5. Delete `bash/doc-comments` and `swift/doc-comments` from each `[[ignore]]`, `--only`, and `--skip`. This release does
   not have these checks, so a command that names one exits with code 2.
6. `.editorconfig` takes its indent from the `format` settings alone, so `bash/shfmt` reports shell scripts that use
   another indent. Write a `[[format.override]]` with the extensions you have, such as `paths = ["**/*.sh"]`, or run
   `gspot check --fix --only bash/shfmt`.
7. If a script reads the JSON output, `gspot doctor --json` has no `suggestions`, and `gspot check --json` prints
   `checks[].command` only with `--verbose`.
