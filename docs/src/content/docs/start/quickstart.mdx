Try gspot on a copy of your repository, then set it up yourself or give one prompt to your coding agent.

## Try gspot on a copy

Run this at the root of a Git repository:

```shell
npx @gspothq/cli scan
```

`gspot scan` copies the files that Git tracks into `.gspot-copies/`, sets up gspot in the copy, installs the tools
there, and runs the checks with no fixes. It then deletes the copy, so your repository does not change.

The report gives the findings by category, with three examples each, and the number of files that differ from your
style. It also gives the cost in tools, megabytes, and seconds, and the plan of `gspot init`. It lists every command
that breaks after init, what init carries over from your configs, what it drops, and the next steps. Add `--markdown` to paste the report into a pull request or a chat, or `--json` to read every finding. A scan exits with
`0` when it prints its report, whatever it finds. npm, uv, and mise keep their download caches, so a second scan
downloads nothing new.

## Set up gspot yourself

You need Git and {`Node.js ${runtimeMinimums.node} or newer`}. Run these commands in the root of your repository.

        </TabItem>

</Tabs>

1. The `add`, `install`, or `use` command adds gspot to the project, pinned to one version. With mise, the command
   before it pins Node.js in `mise.toml`, so that mise does not run gspot with an older Node.js of your system.
2. `gspot init` prints its plan and writes `gspot.toml`, the config files, `AGENTS.md` and the
   rules, and the Git hooks, and deletes the config files it replaces. Run `gspot scan` to
   [read the plan](/start/migrate/#read-the-plan) before you run init.
3. `gspot install` installs the pinned tools and turns on the hooks. From then on, every commit runs the checks.

CI stays off until you enable it. When the repository has GitHub or GitLab CI files, or an `origin` remote on GitHub or
GitLab, `gspot doctor` suggests the commands that enable it.

gspot starts at level `basic`. For stricter checks from the start, run `gspot init --level all`.
[Levels](/start/concepts/#levels) says what each level checks.

## Set up gspot with your coding agent

Paste this prompt into Claude Code, Codex, Cursor, or another coding agent that can run commands.

<Code code={AGENT_PROMPT} lang="text" />

The agent then:

1. Adds `@gspothq/cli` with the package manager of your repository, or pins it with mise.
2. Runs `gspot scan`, and shows you the findings and the plan.
3. Asks which [level](/start/concepts/#levels) you want, and waits for your answer. Then it runs `gspot init` at that
   level, which writes without asking.
4. Runs `gspot install` and `gspot check`, and shows you the result.
5. Reads `AGENTS.md` and the agent rules before it writes more code.

## After you install

Run `gspot check --fix` before your first commit. It formats the files that the checks now cover, such as a
`package.json` or `tsconfig.json` with another indentation, so that the pre-commit hook does not stop the commit.

To accept the findings that remain, run `gspot baseline`. The checks then fail only on new findings; see
[Keep the findings that predate gspot](/use/ignore/#keep-the-findings-that-predate-gspot).

Commit `gspot.toml` and the files that gspot wrote; [Generated files](/reference/generated-files/) lists them. Then
commit as usual. The pre-commit hook checks the staged files and stops the commit when a check fails. Run
`gspot check` to check every file, including work that you did not commit.
