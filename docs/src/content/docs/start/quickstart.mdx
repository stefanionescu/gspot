gspot picks linters and formatters for the languages and frameworks in your repository, and pins each tool that it
installs. Git hooks run the tools before each commit and push, and a problem stops the commit or push. gspot also writes
`AGENTS.md` and rule files that tell coding agents how to write code that passes the checks.

gspot supports JavaScript, TypeScript, Python, Swift, shell scripts, CSS, HTML, SQL, and Markdown. Files in other
languages, such as Go, Rust, or Java, get only the checks that run in every repository, such as the secret scan. The
[configuration reference](/reference/configurations/) lists every language, framework, and tool.

You need Git, {`Node.js ${CLI_REFERENCE.runtimeMinimums.node} or newer`},
{`npm ${CLI_REFERENCE.packageManagerMinimums.npm}, pnpm ${CLI_REFERENCE.packageManagerMinimums.pnpm}, or Bun ${CLI_REFERENCE.packageManagerMinimums.bun} or newer`},
and [mise](https://mise.jdx.dev/). A Yarn project needs npm too. Node.js 22 comes with an npm that is too old, so run
`npm install --global npm@latest`. Without mise, install each tool that `gspot init` names yourself, because a missing
tool stops every commit. A `packageManager` field in `package.json` needs mise, because gspot runs that version through
it.

## Try gspot on a copy

Install your project's dependencies and commit your lockfile, then run this command in the root folder of your Git
repository:

```shell
npx @gspothq/cli scan
```

`gspot scan` sets gspot up in a temporary copy of the files that you committed or staged, and runs the level `basic`
checks there, with no fixes. Your files do not change, but mise installs the tools for your whole machine. The scan skips
your tests, your build, and other checks that run your code. The report lists the checks that it left out. The scan still
loads your Prettier config and runs your installed ESLint, Stylelint, and TypeScript, so run it only on code that you
trust.

The report counts the findings of each kind, such as `Code` or `Secrets`, with examples of each. It lists the files that
`gspot init` writes and deletes, the settings it copies from your old configs, and the scripts and CI steps that call the
old tools. Add `--json` to get every finding.

## Set up gspot

Commit your work first. `gspot init` deletes the tool config files that it replaces, such as `.eslintrc.json`, and runs
only when Git holds each one unchanged, so you can restore it. Old findings in an existing repository then fail the first
commit and push, as [Clean up the first findings](#clean-up-the-first-findings) shows.

gspot starts at level `basic`, which checks for bugs, security problems, code style, broken docs and config, formatting,
and a reason on each suppression. For stricter rules, add `--level all` to the `gspot init` line, or run
`gspot set level all`, then `gspot install`, later. [Levels](/start/concepts/#levels) compares the two.

Run these commands in the root folder of your repository:

`gspot init` prints a plan, then carries it out without asking. It writes `gspot.toml`, a `.gspot/` folder that you
commit, small config files such as `eslint.config.mjs`, and a block in `AGENTS.md`. It also deletes the old tool configs
that it replaces, installs the tools, and turns on the Git hooks. CI stays off until you
[turn it on](/use/ci/#turn-ci-on).

Start each later gspot command the same way as `gspot init`, such as `bunx --no-install gspot check`. These docs write it
as `gspot check`.

## Clean up the first findings

Commit the setup files, then fix each file as you touch it. The setup commit passes once you delete what
`gspot/conflicting-configs` reports and fix or ignore the findings of the files that it stages, such as `package.json` or
an edited CI file. With Bun, pnpm, or Yarn, `dependencies/package-manager-pin` asks for a `packageManager` field in
`package.json`, such as `"packageManager": "bun@<version>"`. `gspot/conflicting-configs` reports old tool settings, and
the scripts, hook lines, and CI steps that still call the old tools. After you edit `package.json`, run the install
command of your package manager and `gspot install`, then stage the result.
[Files to commit](/reference/generated-files/#files-to-commit) lists the setup files.

A later commit checks what you stage, and what your staged change breaks in other files, so touching an old file fails
the commit on that file's old findings. The hook prints a `fix:` line for what a fixer can change. `gspot check --fix` runs
the formatters and the lint fixers. Run them only on the files that you touch, with `gspot check --fix <file>`, because a
repository-wide run rewrites many files, and each then fails on its old lint findings.

On an existing repository, some findings are a matter of taste: `gspot ignore` takes the rule and a reason.

```shell
gspot ignore javascript/eslint --rule no-console --paths "src/legacy/**" --reason "Old code from before gspot."
```

An ignore also hides new findings of that rule in those paths, so name the rule and the paths, and remove the ignore with
`gspot unignore` after you fix the old code.

The first push fails until you fix or ignore the old findings of the checks that read the whole project, such as
`typescript/tsc`, `python/basedpyright`, `javascript/knip`, and your tests. `dependencies/osv-scanner` also runs, because
the setup commit changes the lockfile. `gspot check --only push` shows these findings before you push.

`gspot check` lists every old finding in the repository. Turn on CI after you clear them, because a pull request that
changes `gspot.toml` checks every file. Start an existing repository at `basic`, because level `all` adds checks of the
whole repository, such as `structure/lone-files`, which fail the setup commit until you fix or ignore their findings.

## Set up gspot with a coding agent

Paste this prompt into a coding agent that can run commands, such as Claude Code, Codex, or Cursor:

<Code code={AGENT_PROMPT} lang="text" />

The agent reads the setup steps from `llms.txt`. It runs `gspot scan`, asks you which level to use, and waits for your
answer. Then it runs `gspot init`, deletes the old tool settings that gspot reports, commits the setup, and lists the
remaining findings and what it ignored.
