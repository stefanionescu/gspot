## What you need

gspot runs on macOS, Linux, and Windows. It needs Git, {`Node.js ${runtimeMinimums.node} or newer`},
{`npm ${packageManagerMinimums.npm}, pnpm ${packageManagerMinimums.pnpm}, or Bun ${packageManagerMinimums.bun} or newer`},
and [mise](https://mise.jdx.dev/). With an older Node.js, gspot stops with exit code 2, and with an older package manager,
`gspot init` and `gspot install` stop. Node.js 22 comes with an older npm, so run `npm install --global npm@latest` there.
Without mise, install each tool at its pinned version yourself, because a missing tool stops every commit. A
`packageManager` field in `package.json` needs mise, because gspot runs that version through it.

Run gspot inside a Git working tree, because outside one only `--help` and `--version` work. gspot does not support
sparse checkouts, so run `git sparse-checkout disable` first. gspot runs your tests, your tool configs, and other code
from your repository as your user, and [Trust](/start/concepts/#trust) lists that code.

Each kind of tool needs its own programs:

| Tools                                                    | What you need                                                                                                                                                                                                                   |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tools from npm                                           | Node.js and a package manager. gspot uses the one that `package.json` names in `packageManager` or `devEngines.packageManager`, then the one whose lockfile it finds, and otherwise npm. A Yarn project installs them with npm. |
| Tools from PyPI                                          | uv, which mise installs. When a tool needs Python, gspot installs the Python version that it pins.                                                                                                                              |
| Other tools                                              | mise, or each tool at its pinned version on `PATH`. `gspot doctor` lists the tools that are missing.                                                                                                                            |
| Your project's own commands, such as its tests and build | Your project's runtime, dependencies, and build tools.                                                                                                                                                                          |
| Some checks                                              | The Swift toolchain, a running Docker daemon, or network access. The [configuration reference](/reference/configurations/) says what each check needs.                                                                          |

`gspot install` downloads from these hosts, which a firewall must allow:

- the npm registry, or the registry that `.npmrc` names, for the npm tools
- `github.com` and `api.github.com`, for the mise tools, the tree-sitter grammars, and the Vale packages
- `pypi.org` and `files.pythonhosted.org`, for the Python tools

`gspot install` stops when a pinned tool came out less than `dependencies.min_release_age_days` days ago, as
[Upgrade](/start/upgrade/) describes.

## Add gspot

These docs write each command as `gspot <command>`. To run one, start it the way the last column shows, such as
`pnpm exec gspot check`. A repository without a `package.json`, such as a Python or Swift project, uses mise, which
records the gspot version in `mise.toml`.

## Set up a clone

In a new clone, first install the dependencies from the committed lockfile, which sets the gspot version of the clone.
Without a `package.json`, `mise.toml` sets it. Then run `gspot install`, because `gspot init` refuses to run when
`gspot.toml` exists.

`gspot install` installs the tools and turns on the Git hooks in the clone. If it changes a lockfile under `.gspot/`,
commit that file.

`gspot install` installs a tool from mise only when one of its checks has a file to read. The files under `.gspot/` pin
every tool either way. After you add the first file of a new kind, such as the first `.env` file, its check reports the
tool as missing until you run `gspot install` again.

## If your package manager refuses a new gspot release

Some package managers refuse a version until it is a set age, as pnpm 11 does for one day by default. To install a gspot
release on the day it comes out, exclude the gspot packages from that wait:

## Private registries

When gspot installs its tools with npm, pnpm, or Bun, it reads the registry settings from `.npmrc` and from your
environment. A Yarn project installs them with npm, so gspot reads `.npmrc`, not `.yarnrc.yml`. uv reads the Python
package indexes from `uv.toml` or from `[tool.uv]` in `pyproject.toml`.

Keep credentials in environment variables or in your user settings, not in `gspot.toml` or a lockfile.

## Uninstall

To stop checking one language or framework, [remove its configuration](/configure/gspot-toml/#add-or-remove-a-configuration)
instead. To remove gspot, commit first, so that you can go back, then follow these steps:

1. Turn off the rules for coding agents and the CI job. gspot then deletes the rule files, its block in `AGENTS.md`,
   and the CI workflow:

    ```shell
    gspot set rule_files.enabled false
    gspot set ci.enabled false
    ```

2. Turn off the Git hooks with `git config --unset core.hooksPath`. If Husky, Lefthook, or your own hooks call gspot,
   delete those lines.
3. Write down the paths in the gspot block of `.gitattributes`. They are the generated files outside `.gspot/`.
4. Delete those files, the gspot block of `.gitattributes`, `gspot.toml`, and `.gspot/`. If the gspot block was all that
   `.gitattributes` held, delete the file.
5. Remove the gspot package with your package manager, or run `mise unuse npm:@gspothq/cli`.
6. Restore the tool configs that you want back from Git, for example with `git show <commit>:.eslintrc.json`.

Git stores `core.hooksPath` in each clone, and a pull does not change it. After they pull the removal, each teammate
also runs `git config --unset core.hooksPath`.

To undo the removal, check out the commit that you made first, and run `gspot install`.
[Files and caches](/reference/generated-files/#caches-outside-the-repository) lists what gspot leaves on your machine.
