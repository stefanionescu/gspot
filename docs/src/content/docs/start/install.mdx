## What you need

Git and {`Node.js ${runtimeMinimums.node} or newer`}. An older Node.js stops gspot with exit code 2 and names the version it
found:

<Code code={`gspot needs Node.js ${runtimeMinimums.node} or newer (found 22.11.0).`} lang="text" />

Run gspot in a full Git worktree; only help and version work outside one. For a sparse checkout, run
`git sparse-checkout disable` first.

gspot runs the code of your repository, such as its tests and tool configs, as your user. See
[Trust](/start/concepts/#trust).

The tools that your checks run need these:

| Tools                                                    | What you need                                                                                                                                                                                                                 |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tools from npm                                           | Node.js and npm, pnpm, or Bun. gspot uses npm for Yarn projects. gspot uses the package manager that `package.json` names in `packageManager` or `devEngines.packageManager`, else the one whose lockfile it finds, else npm. |
| Tools from PyPI                                          | uv; gspot installs its pinned Python version when needed.                                                                                                                                                                     |
| Other tools                                              | mise, or the exact pinned tools on `PATH`. `gspot doctor` lists missing tools.                                                                                                                                                |
| Your project's own commands, such as its tests and build | Your project's runtime, dependencies, and build tools.                                                                                                                                                                        |

`gspot install` needs a package manager that can hold back new releases:
{`npm ${packageManagerMinimums.npm}, pnpm ${packageManagerMinimums.pnpm}, or Bun ${packageManagerMinimums.bun} or newer`}.
Node.js 22 ships an older npm, so run `npm install --global npm@latest` there.

`gspot install` downloads from these hosts:

- the npm registry, or the registry that `.npmrc` names, for the npm tools
- `github.com` and `api.github.com`, for the mise tools, the tree-sitter grammars, and the Vale packages
- `pypi.org` and `files.pythonhosted.org`, for the Python tools

### Systems

gspot runs on macOS, Linux, and Windows. Some checks need macOS or Linux, the Swift toolchain, a running Docker daemon,
or network access. The section of each check in the [configuration reference](/reference/configurations/) says what it
needs.

## Add gspot

These docs write each command as `gspot <command>`. Start it the way your package manager runs a local program, as the
last column shows. A repository without `package.json`, such as a Python or Swift project, uses mise, which pins gspot
in `mise.toml`.

`allow_low_downloads=true` approves gspot.

## Set up a clone

Install the dependencies from the committed lockfile first; it pins the gspot version of the repository. Without
`package.json`, `mise.toml` pins it. `gspot init` refuses to run where `gspot.toml` exists, so run `gspot install`
instead.

`gspot install` installs the tools and turns on the hooks in this clone. If it changes a lockfile under `.gspot/`, commit
that file. A second run installs only what changed: each package manager skips the packages it already installed, and
the Vale download runs only when `.gspot/vale/` lacks a package or holds other releases.

## Install a release on the day it ships

A package manager can hold back versions younger than a set age; pnpm 11 holds each version for one day by default. To
install a gspot release on the day it ships, exempt its packages:

## Private registries

The npm, pnpm, and Bun installs of gspot read registry settings from `.npmrc` and your environment. For Yarn projects,
gspot installs its tools with npm and reads `.npmrc`, not `.yarnrc.yml`. uv reads Python package indexes from
`uv.toml` or `[tool.uv]` in `pyproject.toml`.

Keep credentials in environment variables or your user settings, never in `gspot.toml` or a lockfile.

## Uninstall

To stop checking one language or framework instead, see
[Add or remove a configuration](/configure/gspot-toml/#choose-configurations).

Commit first, so that you can go back.

1. Turn off the agent rules and CI. gspot deletes the rule files, its block in `AGENTS.md`, and the CI workflow:

    ```shell
    gspot set rule_files.enabled false
    gspot set ci.enabled false
    ```

2. Turn off the hooks with `git config --unset core.hooksPath`. If Husky, Lefthook, or your own hooks call gspot,
   delete those lines.
3. Note the paths in the gspot block of `.gitattributes`. They are the generated files outside `.gspot/`.
4. Delete those files, the gspot block of `.gitattributes`, `gspot.toml`, `gspot.baseline.json`, and `.gspot/`. Delete
   `.gitattributes` when the gspot block was all it held.
5. Remove the package with your package manager, or run `mise unuse npm:@gspothq/cli`.
6. Restore the tool configs you want from Git, such as `git show <commit>:.eslintrc.json`.

Each teammate runs `git config --unset core.hooksPath` after pulling the removal, because Git keeps that setting in
each clone.

To undo, check out the commit that you made first, and run `gspot install`. [Files and caches](/reference/generated-files/#caches-outside-the-repository)
lists what stays on your machine.
