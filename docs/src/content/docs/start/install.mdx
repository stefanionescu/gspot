## What you need

Git and {`Node.js ${RUNTIME_MINIMUMS.node} or newer`}. When Bun runs gspot, it needs {`Bun ${RUNTIME_MINIMUMS.bun} or
newer`}. An older runtime stops gspot with exit code 2 and names the version it found:

<Code code={`gspot needs Node.js ${RUNTIME_MINIMUMS.node} or newer (found 22.11.0).`} lang="text" />

The tools that your checks run need these:

| Tools                                                    | What you need                                                                                                                                                                                                                        |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Tools from npm                                           | Node.js and the npm, pnpm, Yarn, or Bun package manager of the project. gspot uses the package manager that `package.json` names in `packageManager` or `devEngines.packageManager`, else the one whose lockfile it finds, else npm. |
| Tools from PyPI                                          | uv; gspot installs its pinned Python version when needed.                                                                                                                                                                            |
| Other programs                                           | mise, or the exact pinned tools on `PATH`. `gspot doctor` lists missing tools.                                                                                                                                                       |
| Your project's own commands, such as its tests and build | Your project's runtime, dependencies, and build tools.                                                                                                                                                                               |

`gspot init --dry-run` shows the configurations that gspot picks. After init, `gspot doctor` lists the missing tools.

### Systems

gspot runs on macOS, Linux, and Windows. Some checks need macOS or Linux, the Swift toolchain, a running Docker daemon,
or network access; each [check page](/reference/checks/) says what it needs.

## Choose how to install

Install gspot with the package manager of your repository. A repository without `package.json`, such as a Python or
Swift project, uses mise, which pins gspot in `mise.toml`. The guides show commands as `gspot ...`; start them as the
last column shows.

`allow_low_downloads=true` approves gspot.

## Set up a clone

Install the dependencies from the committed lockfile first; it pins the gspot version of the repository. Without
`package.json`, `mise.toml` pins it. When the versions differ, gspot stops with `This repository pins gspot <version>`
and prints the install command. `gspot init` refuses to run where `gspot.toml` exists, so run `gspot install` instead.

`gspot install` installs the tools and turns on hooks in this clone. If it changes a lockfile under `.gspot/`, commit
that file.

## A hold on new releases

A package manager can hold back versions younger than a set age; pnpm 11 holds each version for one day by default. To
install a gspot release on the day it ships, exempt its packages:

## Private registries

The npm, pnpm, Yarn, and Bun installs of gspot use the registry settings of your repository and your environment. uv
reads Python package indexes from `uv.toml` or `[tool.uv]` in `pyproject.toml`.

Keep credentials in environment variables or your user settings, never in `gspot.toml` or a lockfile.

## Uninstall gspot

To stop checking one language or framework instead, see [gspot.toml](/configure/gspot-toml/#choose-configurations).

Commit first, so you can go back.

1. Copy the list under "Generated files" in the managed block of `AGENTS.md`, the part between the gspot markers. It
   names every file gspot writes outside `.gspot/` and each key it sets in your files.
2. Run `gspot set rules.enabled false`, `gspot set ci.enabled false`, and `gspot set hooks.enabled false`, then
   `gspot install`. gspot deletes the rules, its `AGENTS.md` managed block, the CI workflow, and the hook scripts, and
   `gspot install` removes `core.hooksPath`. If Husky, Lefthook, or your own hooks run gspot, delete those lines.
3. Restore your earlier config files from Git, such as `git show <commit>:.eslintrc.json`, or set up the tools you want.
4. Delete the files and keys from step 1, the managed blocks in `.gitignore` and `.gitattributes`, `gspot.toml`, and
   `.gspot/`.
5. Remove the package: `bun remove @gspothq/cli`, the remove command of your package manager, or
   `mise unuse npm:@gspothq/cli`.

Review the diff. To undo, go back to the first commit and run `gspot install`.
