## What you need

Git and {`Node.js ${runtimeMinimums.node} or newer`}. An older Node.js stops gspot with exit code 2 and names the version it
found:

<Code code={`gspot needs Node.js ${runtimeMinimums.node} or newer (found 22.11.0).`} lang="text" />

Run gspot in a full Git worktree; only help and version work outside one. For a sparse checkout, run
`git sparse-checkout disable` first.

The tools that your checks run need these:

| Tools                                                    | What you need                                                                                                                                                                                                                 |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tools from npm                                           | Node.js and npm, pnpm, or Bun. gspot uses npm for Yarn projects. gspot uses the package manager that `package.json` names in `packageManager` or `devEngines.packageManager`, else the one whose lockfile it finds, else npm. |
| Tools from PyPI                                          | uv; gspot installs its pinned Python version when needed.                                                                                                                                                                     |
| Other programs                                           | mise, or the exact pinned tools on `PATH`. `gspot doctor` lists missing tools.                                                                                                                                                |
| Your project's own commands, such as its tests and build | Your project's runtime, dependencies, and build tools.                                                                                                                                                                        |

`gspot install` needs a package manager that can hold back new releases:
{`npm ${packageManagerMinimums.npm}, pnpm ${packageManagerMinimums.pnpm}, or Bun ${packageManagerMinimums.bun} or newer`}.
Node.js 22 ships an older npm, so run `npm install --global npm@latest` there.

`gspot init` prints the configurations it selects, writes its plan without asking, and installs the tools. `gspot scan`
prints the plan of the default level and changes nothing in your repository. After init, `gspot doctor` lists the
missing tools.

### Systems

gspot runs on macOS, Linux, and Windows. Some checks need macOS or Linux, the Swift toolchain, a running Docker daemon,
or network access; the section of each check in the [configuration reference](/reference/configurations/) says what it
needs.

## Choose how to install

Install gspot with the package manager of your repository. A repository without `package.json`, such as a Python or
Swift project, uses mise, which pins gspot in `mise.toml`. The guides show commands as `gspot ...`; start them as the
last column shows.

`allow_low_downloads=true` approves gspot.

## Set up a clone

Install the dependencies from the committed lockfile first; it pins the gspot version of the repository. Without
`package.json`, `mise.toml` pins it. `gspot init` refuses to run where `gspot.toml` exists, so run `gspot install`
instead.

`gspot install` installs the tools and turns on hooks in this clone. If it changes a lockfile under `.gspot/`, commit
that file. A second run installs only what changed: each package manager skips the packages it already installed, and
the Vale download runs only when `.gspot/vale/` lacks a package or holds other releases.

## A hold on new releases

A package manager can hold back versions younger than a set age; pnpm 11 holds each version for one day by default. To
install a gspot release on the day it ships, exempt its packages:

## Private registries

The npm, pnpm, and Bun installs of gspot read registry settings from `.npmrc` and your environment.
For Yarn projects, gspot installs its tools with npm and reads `.npmrc`, not `.yarnrc.yml`.
uv reads Python package indexes from `uv.toml` or `[tool.uv]` in `pyproject.toml`.

Keep credentials in environment variables or your user settings, never in `gspot.toml` or a lockfile.

## Uninstall gspot

To stop checking one language or framework instead, see [gspot.toml](/configure/gspot-toml/#choose-configurations).

Commit first, so you can go back.

1. Save the paths marked `linguist-generated` in the gspot block of `.gitattributes`. It lists the generated files
   outside `.gspot/`. Review [Generated files](/reference/generated-files/) for keys gspot sets in your own files.
2. Run `gspot set rule_files.enabled false` and `gspot set ci.enabled false`. gspot deletes the rules, its `AGENTS.md`
   managed block, and the CI workflow. Then run `git config --unset core.hooksPath`. If Husky, Lefthook, or your own
   hooks run gspot, delete those lines.
3. Restore your earlier config files from Git, such as `git show <commit>:.eslintrc.json`, or set up the tools you want.
4. Delete the generated files and tool keys identified in step 1, the managed block in
   `.gitattributes` and the blank line above it, `gspot.toml`, and `.gspot/`.
5. Remove the package: `bun remove @gspothq/cli`, the remove command of your package manager, or
   `mise unuse npm:@gspothq/cli`.

Review the diff. To undo, go back to the first commit and run `gspot install`.

The hooks run the code of the repository as you; see [Trust](/start/concepts/#trust).

## What stays outside the repository

Deleting `.gspot/` leaves global mise tools, uv-managed Python versions, and the Swift build cache of gspot.
[Files and caches](/reference/generated-files/#caches-outside-the-repository) lists their locations and the commands to prune
unused tools and caches. Check for leftover `.gspot-copies/` folders after all checks stop.
