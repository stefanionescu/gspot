Framework configurations, such as `react`, `nextjs`, and `react-native`, add their own lint rules. A React project that
depends on `react-dom` also gets the `react-dom` configuration and its DOM accessibility lint rules. The
[configuration reference](/reference/configurations/) lists every framework.

## JavaScript runtimes

Each file gets one ESLint runtime:

| Files                                      | Runtime                                                   |
| ------------------------------------------ | --------------------------------------------------------- |
| Ordinary modules and build scripts         | Node.js built-ins                                         |
| `.cjs` and `.cts` files                    | Node.js built-ins and CommonJS globals                    |
| React, Vue, and Svelte application sources | Browser globals                                           |
| React Native sources                       | Native globals                                            |
| Next.js sources                            | Node.js built-ins, because server components can use them |

To give some files another runtime, add a `[[tools.eslint.override]]` record. Write paths relative to the repository
root. When records overlap, the later one counts.

```toml title="gspot.toml"
[[tools.eslint.override]]
paths = ["src/client/**"]
runtime = "browser"

[[tools.eslint.override]]
paths = ["src/workers/**"]
runtime = "worker"

[[tools.eslint.override]]
paths = ["src/serviceworker.js"]
runtime = "serviceworker"
```

Use an explicit `node` runtime for server code inside a browser or React Native project. Runtime names follow the
pinned [globals package](https://github.com/sindresorhus/globals). Use `serviceworker` for service workers, which have
other APIs than Web Workers. An unknown runtime name stops ESLint when it loads the config, and the error lists the
names that the globals package knows.

Browser and native files get no Node.js lint rules. React Native files keep the `process` and `require` globals, but
get no other Node.js globals, such as `Buffer` and `__dirname`.

## TypeScript compiler

gspot runs the TypeScript checks when the project has TypeScript source files or a `tsconfig.json` of its own. A
TypeScript tool dependency or declaration files alone do not count.

- With your own `tsconfig.json`, gspot keeps your compiler options and adds the strict options that the level needs.
- Without one, gspot writes a project for the source files of each scope. It leaves out generator output, vendored
  files, and child scopes.
- gspot uses the TypeScript compiler of your project, for the type checks and for the type-aware lint rules. Without
  one, it uses the compiler that `gspot install` pins.

JavaScript files get the same check through your `jsconfig.json`, or through your `tsconfig.json` when no
`jsconfig.json` exists.

## Import extensions

`javascript.import_extension` decides how a relative import of a code file ends: `js`, `ts`, or `extensionless`.
`gspot init` picks it from the project:

| Project                                                                                  | Style           |
| ---------------------------------------------------------------------------------------- | --------------- |
| The tsconfig sets `allowImportingTsExtensions` or `rewriteRelativeImportExtensions`      | `ts`            |
| The tsconfig uses `Bundler` resolution, or the project depends on a bundler such as Vite | `extensionless` |
| Any other project                                                                        | `js`            |

A framework configuration that chooses a style wins over the project. An import of a stylesheet or a JSON file
keeps its extension. `.mjs` files, `.cjs` files, and Node.js shebang scripts always import the full file name, because
Node.js needs it, and they take aliases only from the `imports` of `package.json`.

For modules that a host application provides at run time, see
[modules that the host provides](/configure/import-rules/#modules-that-the-host-provides).

## Next.js

The Next.js configuration runs `nextjs/tsc` instead of `typescript/tsc`, at level `basic` and stage `push`. The
check has Next.js write its types, then type-checks the app with the strict compiler options. The project must provide
Next.js 15.5 or later. The Next.js security rules run in `javascript/eslint`.

## React Native

`gspot init` selects `react-native` and `expo` from their dependencies. The Expo configuration requires React Native and
adds Expo lint rules and `expo/expo-doctor`. A bare React Native project needs no Expo tool. Native sources keep the
React hooks and component lint rules.

If a component wraps the React Native `Text`, add its name to the `skip` option of the lint rule:

```shell
gspot set tools.eslint.rules '{ "react-native/no-raw-text" = [{ skip = ["ThemedText"] }] }'
```

This allows text inside `ThemedText`. The lint rule still reports bare text inside a `View`. When other projects use
other components, set the option in the scope of the native project.
