gspot checks shell scripts for mistakes with ShellCheck, and for layout with shfmt. It checks the syntax of Zsh scripts
with `zsh -n`. The `bash` configuration runs these checks:

## When gspot turns it on

gspot turns on `bash` in a scope that has a file ending in `.sh`, `.bash`, `.zsh`, or `.bats`. A file with any other
name also counts when its shebang, the `#!` line at the top, names `bash`, `sh`, `zsh`, `dash`, `ksh`, or `bats`.

Each tool reads the scripts of its own shell:

| Scripts                          | Tools                                      |
| -------------------------------- | ------------------------------------------ |
| Bash, `sh`, `dash`, and bats     | ShellCheck and shfmt                       |
| Zsh                              | `zsh -n`, through `bash/zsh-syntax`        |
| Every shell script, ksh included | The built-in checks, such as `bash/safety` |

ShellCheck reads a script without a shebang as Bash, and it reads each file that a script loads with `source`.
`bash/zsh-syntax` runs the `zsh` that your system has, and `gspot install` does not install it, so install Zsh yourself
when your repository has Zsh scripts.

## Levels

At level `basic`, ShellCheck runs its default checks, and `bash/safety` reports commands that kill processes by name,
such as `killall`, and recursive deletes. It also reports `eval`, `curl` without `--fail`, `typeset`, `|&`, `bash -lc`,
and GNU `timeout`.

At level `all`, gspot turns on these optional ShellCheck checks: `add-default-case`, `avoid-negated-conditions`,
`avoid-nullary-conditions`, `check-extra-masked-returns`, `check-set-e-suppressed`, `check-unassigned-uppercase`,
`deprecate-which`, `quote-safe-variables`, `require-double-brackets`, `require-variable-braces`, and
`useless-use-of-cat`.

A script that pipes a download into a shell gets two findings at both levels:

```bash title="scripts/deploy.sh"
curl https://example.com/install.sh | bash
```

```text
failed   bash/safety  2 findings
  scripts/deploy.sh:1  curl-fail  Pass `--fail`, so that an HTTP error stops the script.
  scripts/deploy.sh:1  curl-pipe-shell  Nobody can read a script that runs as it downloads. Download it to a file, check it, then run it.
```

## Settings

shfmt reads its layout options from `.editorconfig`, which gspot writes from the `format` settings. When most lines of
your `.sh` and `.bash` files use another indent, `gspot init` writes a `[[format.override]]` record for them, and you
change the indent in that record. shfmt also indents the branches of a `case` statement and simplifies code, such as
removing `$` inside `$(( ))`.

At level `all`, `bash/function-size` allows each shell function 40 lines, 8 branches, 3 levels of nesting, and 8
assignments. The settings are `limits.bash.max_function_lines`, `limits.bash.max_function_branches`,
`limits.bash.max_block_nesting`, and `limits.bash.max_function_assignments`, and raising one needs a reason:

```shell
gspot set limits.bash.max_function_lines 60 --reason "The deploy script keeps its steps in one function."
```

To turn off one ShellCheck code, ignore it with a reason:

```shell
gspot ignore bash/shellcheck --rule SC2086 --reason "The build flags split into words on purpose."
```

To allow one line only, add a ShellCheck comment with a reason, such as
`# shellcheck disable=SC2086 # reason: the word splitting is wanted here`.

## What gspot accepts

ShellCheck skips four codes in `.bats` files that do not fit how bats runs tests. At level `all`, the naming checks
accept the variables that the shell defines, such as `IFS`, `OPTARG`, `BASH_SOURCE`, and `PIPESTATUS`. They also ignore
a leading underscore, which marks a private function or variable.
