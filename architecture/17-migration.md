# Migration

This document decides the two goals gspot is built against and what `gspot init` does to a repository that already has home-grown linting. It also shows what that repository looks like when the migration is done.

The reference comparison order is yap-swift-app, yap-text-inference, yap-landing, slopshop, and
the two ComfyUI nodes. Only the real yap-swift-app migration is authorized, after the gate in
[22-remaining.md](22-remaining.md). Other sheets are design inputs, not permission to install,
delete, or run migration acceptance in those repositories. Ask the owner for each one (D-121).

## The two goals

1. **gspot lints gspot.** Full strictness, no ignores, from Phase 0 (D-27). The self-lint is the
   first integration test and runs on every change.
2. **gspot replaces the home-grown linting in the six reference repositories.** Every rule and
   check in their `quality/` folders, dotfiles, hooks and task runners lands in a gspot check
   ([06-enforcement-ledger.md](06-enforcement-ledger.md)). The acceptance harness proves it in a detached worktree.

The migration itself, deleting what gspot made redundant, is the owner's step, guided by the plan `init` prints (D-57). gspot lists; the person deletes.

What this repository taught, and the rule each lesson landed as. None is a special case: each is
one general mechanism or one corrected default.

- **A repository can need checks gspot does not ship.** Type checking per engine under `uv run --extra`, Linux only. The answer is the `[[check]]` entry that already existed, now with `platform`. A person declares the command, and gspot schedules, caches, and skips it like any preset check.
- No preset grew a slot for it.
- **Takeover reads conventional paths and nothing else.** A shellcheckrc inside `quality/` is
  invisible, and gspot does not go looking. The person moves the exception lists first.
- **The cyclomatic limit was wrong in the ledger.** Every source repository uses 8; the ledger
  said 10. D-20 says the strictest observed ships, so the default is 8.
- **A document that tells the reader to run a task that does not exist is drift.**
  `docs/stale-paths` treats a task name like a path.
- **A manifest whose dependencies are all pinned tools is redundant.** One rule, any manifest,
  root or workspace; under mise the npm tools become `npm:` pins and a Python repository keeps no
  Node footprint.
- **A default must not tighten by accident.** With no `[[scope]]`, commitlint has no scope enum.

- **One language, several runtimes.** A file's runtime comes from what references it (a

## How the migration runs

The branch operations, baseline verification, and candidate installation are specified once in
[22-remaining.md](22-remaining.md). Use its gated procedure before these steps:

1. Inventory existing tooling, configuration, exceptions, hooks, and non-lint files sharing a
   lint directory. Classify each as carried, replaced, retained, or developer cleanup. Unsupported
   configuration stays in place. Do not move or delete an entire folder to make detection pass.
1. Run `gspot init`, read the complete plan, and confirm only the understood replacements.
   Recovery records must exist before any replacement or deletion, under
   [03-configuration.md](03-configuration.md). Git history alone is not the recovery mechanism.
1. Run `gspot check --no-cache`, `gspot check --stage manual --no-cache`, and `gspot doctor`.
   Review every finding and inspect all written files. A changed-file gate can still report
   errors from unchanged files in an affected whole-project check. No baseline hides them.
1. Remove only verified obsolete files and entries identified in the plan. Preserve unrelated
   tasks, user hooks, shared manifests, unsupported settings, and developer-owned rule files.
   Compare old and replacement enforcement before removing the old check. Rerun checks after
   cleanup; a missing replacement blocks that deletion.
1. Review each carried exception and record its retained meaning or justified removal. Remove
   old lint documentation only after the replacement explains the corresponding workflow.
1. Produce the migration report and inspect the complete diff. Leave it uncommitted unless
   committing was authorized. An authorized commit requires `gspot check --staged` as its
   last check and passing hooks, never `--no-verify`.

Automated acceptance uses planted test data and explicitly authorized disposable repositories.
It does not grant permission to install into every named real reference repository on a release.
The real app migration is a separate deliverable, not a substitute for the test repository suite.
