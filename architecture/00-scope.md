### APIs

Yes, and split into two, because `yap-swift-app/rules/API.md` mixes them.

| Preset                | Holds                                                                                                                                                                                           | Architecture it assumes                                 |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| shared `http`       | A contract exists per route, requests validate at the boundary, one error shape, no internal detail in a response, status semantics, generated OpenAPI matches the code, every route has a test | None. Express, Fastify, Hono and Elysia all satisfy it. |
| `framework:fastapi` | Router composition, `Depends` injection, Pydantic at the boundary, `response_model` declared, lifespan handlers, no blocking IO in an async route, OpenAPI freshness                            | Only what FastAPI itself requires                       |

Plus `spectral` for OpenAPI document linting, which the reference monorepo generates and lints with
nothing.

What does **not** come from a preset: the ownership map, the module boundary table, the endpoint
directory layout, the domain and service and data-access layers, and the provider-integration
pattern. Roughly 600 lines of `rules/API.md`. Those are one team's architecture and they land in
`rules/project/`, which the consumer owns. [10-rules.md](10-rules.md) has the line-by-line split.

Three presets, so the general work is reusable and the product-specific work is thin.

| `language:sql`       | SQL as a language | any dialect          |

A Neon project selects two presets and gets nine checks. A Supabase project selects three and gets

## Non-requirements, stated so nobody assumes them

- **gspot is not a language server.** Editor integration happens because gspot writes real config
  files at conventional paths, not through a protocol.
- **gspot does not host its own analysis for what a tool already does.** The orchestrator runs
  ESLint, Ruff, SwiftLint and the rest. It adds analysis only where the structure engine has no
  off-the-shelf equivalent.
- **gspot does not run continuous integration.** It emits a CI workflow when the GitHub CI emitter
  preset is selected, and that preset is off by default because one reference repository wants no
  `.github/`.
- **gspot does not manage product configuration.** The `yap-swift-app` defect where an nginx image
  tag and an upstream host live inside the lint package is a class of mistake the design forbids: a
  preset reads a product fact from the product file, or it does not know the fact.
- **gspot does not support a warning layer.** Every rule that runs is an error. There is no `warn`
  severity, no `--max-warnings` above zero, and no run-but-do-not-fail mode of the kind MegaLinter's
  `DISABLE_ERRORS_LINTERS` provides. Adoption uses a time-boxed baseline with a decreasing baseline
  and a required expiry.
- **gspot does not lint 67 languages.** It covers ten completely, including the structural and
  naming rules no aggregator ships, and adds an eleventh when a reference repository needs it.
  Breadth is what MegaLinter is for.

## Definition of done for the architecture

The design is complete when a reader can answer these without guessing:

1. Given a repository, which files does gspot claim, and which tool claims each?
1. Which files does gspot not claim, and under which declared status?
1. Where does a consumer add an allowed typo, and what stops that edit from turning into a disabled
   rule?
1. Which task runs which check at which stage, and what happens when the tool is missing?
1. Which rule file does an agent read for a TypeScript change in a Next.js app, and which
   architecture does that file assume?

[18-proof.md](18-proof.md) answers all five against a real tree.
