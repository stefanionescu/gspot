# File Tree

This document decides every folder and file in gspot's repository. Implementation puts a file
where this document says or changes this document in the same commit. Names follow the naming
policy gspot ships: kebab-case files, no `util`, `helper`, `common`, `core`, `lib` or `misc`,
no folder with one code file, types under `types/`.

Where a pattern repeats (one file per command, one per check, one per preset), the pattern is
stated once and the full list follows it, so the tree is complete without listing the same
shape forty times.

## Root

```text
gspot/
├── .changeset/                 changesets: config.json, README.md, one file per pending change
├── .github/
│   ├── workflows/
│   │   ├── ci.yml              unit, rule, snapshot, planted-repository and self-lint suites on ubuntu, macos, windows
│   │   ├── release.yml         build five binaries, attest, GitHub release, npm publish, docs deploy
│   │   └── gspot.yml           gspot's own gate, generated by gspot (header, guarded by sync --check)
│   └── CODEOWNERS
├── .gspot/                     gspot's own generated files (the same layout every repository gets; see below)
├── .mise/
│   └── conf.d/
│       └── gspot.toml          generated: gspot's own tool pins and tasks
├── architecture/               this folder
├── docs/                       the manual (Starlight site); see Docs
├── packages/
│   ├── cli/                    the binary
│   ├── eslint-plugin/          eslint-plugin-gspot
│   └── npm/                    the npm launcher and the platform package template
├── presets/                    one folder per preset
├── prose/                      the gspot Vale style
├── rules/                      the agent rule corpus, by layer
├── schema/
│   ├── gspot.schema.json       generated from the zod schema; published with each release
│   └── run-record.schema.json  generated; the shape of check --json and .gspot/last.json
├── tests/                      the suites that need a repository or a registry; see Tests
├── AGENTS.md                   one managed block (gspot writes it) and nothing else
├── CLAUDE.md                   same
├── CHANGELOG.md                written by changesets
├── LICENSE.md
├── README.md
├── bunfig.toml                 minimumReleaseAge and the security scanner (gspot's own install policy)
├── gspot.toml                  gspot's own policy, written by gspot init, no ignores (D-27)
├── mise.toml                   bun, and nothing gspot pins itself
├── package.json                workspace root: packages/*, private
└── tsconfig.json               extends .gspot/tsconfig.base.json
```

`reference-rules/` exists today and is interim: its `merged/` tree becomes `rules/` and its
`lint/` scripts become `packages/cli/src/rules/` in Phase 6. The completeness check and
`DROPPED.md` stay under `reference-rules/` until the source corpora are removed, then the folder
goes.

### `src/commands/`

Fifteen files, one per command, each under sixty lines: `init.ts`, `check.ts`, `sync.ts`,
`ignore.ts`, `add.ts`, `remove.ts`, `allow.ts`, `set.ts`, `declare.ts`, `why.ts`, `explain.ts`,
`doctor.ts`, `upgrade.ts`, `uninstall.ts`, `completion.ts`. A command file registers its flags
with commander, calls one function from another folder, and hands the result to `output/`. No
logic lives here.

### `src/config/`

| File | Holds |
| --- | --- |
| `schema.ts` | the zod schema of `gspot.toml`: presets, scopes, limits (root and per language), naming, architecture, structure, tools, ignore, declare, check, hooks, ci, rules, editor, coverage, runner |
| `local-schema.ts` | the one-key schema of `gspot.local.toml` |
| `load.ts` | read, parse (smol-toml), validate, resolve scopes; every load error through `zod-validation-error` and `messages.ts` |
| `merge.ts` | preset default, framework override, scope table, root table; lists append, scalars replace, conflicts fail |
| `write.ts` | the one writer the six commands share: `toml-patch` append, replace, remove; validate as load; run sync |
| `reasons.ts` | the refused reasons (`N/A`, `TBD`, empty) and the loosening-needs-a-reason rule |
| `settings.ts` | the settings surface: every key, its direction, its default, its source, for `set`, `doctor --settings` and the docs |
| `messages.ts` | every load and write message in plain English, one function per message, tested |
| `json-schema.ts` | `z.toJSONSchema` into `schema/gspot.schema.json` and `run-record.schema.json` |

`source-bans.ts` (`<!-- vale` directives, `/* */` in SQL), `vocabulary.ts` (`[prose]` into the

`config-purity.ts`, `css-usage.ts`, `dependency-alignment.ts`, `dependency-ownership.ts`,
`docs-headings.ts`, `docs-links.ts`, `env-files.ts`, `generated-drift.ts`,

### `src/rules/`

`assemble.ts` (select files for the selection, write under `[rules] directory`, remove
strays), `managed-block.ts` (the index block for `CLAUDE.md` and `AGENTS.md`),
`front-matter.ts`, `markers.ts` (`enforced-by` and `unenforced`, the count),
`corpus-lint.ts` (front matter, ids, links, size, layer boundary, fences, corruption, Vale),
`templates.ts` (project templates: copy once, the `gspot-template` header, the upstream-changed
report). `completeness-check.ts` stays under `reference-rules/lint/` until the source corpora
are removed.

### `src/doctor/`

`probes.ts` (locate and version every tool: `node_modules/.bin`, `.venv/bin`, mise shims,
`PATH`), `coverage.ts` (unchecked and partial files), `changes.ts` (detected not selected,
configuration not owned, changed outside gspot, each with its command), `settings.ts` (the
`--settings` listing), `newer-version.ts` (`latest-version`, once, when a person runs it).

### `src/output/`

`reporter.ts` (check lines, findings, `help:` lines, reproduce lines, the summary; columns from
the longest id), `messages.ts` (`consola` on stderr with levels), `plan.ts` (the `init`,
`upgrade` and `--dry-run` plans), `json.ts` (the documented object per command), `prompts.ts`
(the clack questions, skipped without a terminal), `explain.ts` (check, tool rule, preset,
setting; tool rule text from `ruff rule`, `swiftlint rules`, ESLint `meta.docs`, markdownlint
metadata), `why.ts`, `completion.ts` (`@bomb.sh/tab` adapter).

### `src/platform/`

`paths.ts` (`node:path`, forward slashes in selectors, the platform form for tools),
`spawn.ts` (`Bun.spawn`, `cross-spawn` for `.cmd` shims), `executable-bit.ts`
(`git update-index --chmod=+x`), `install-hints.ts` (mise, Homebrew, apt, winget, scoop per
platform).

### `types/`

`config.ts`, `manifest.ts`, `finding.ts`, `run-record.ts`, `repository.ts`, `render.ts`,
`naming.ts`, `structure.ts`, `doctor.ts`. Type aliases only; no runtime export.

## What is not in the tree

- No `scripts/` folder: build steps are `build.ts` in each package and `docs/generate.ts`;
  release steps are the workflow.
- No `src/index.ts` or barrel anywhere; `plugin.ts` is the ESLint plugin's entry because ESLint
  needs an object, and `main.ts` is the binary's.
- No `examples/`: the planted repositories are the examples and the docs link to them.
- No per-preset `docs/` folder: the corpus is one tree under `rules/` and manifests name files
  in it by path.
