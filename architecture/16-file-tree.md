# File Tree

This document decides every folder and file in the gspot repository. Implementation puts a file
where this document says or changes this document in the same commit. Names follow the naming
policy gspot ships: kebab-case files, no `util`, `helper`, `common`, `core`, `lib` or `misc`,
no folder with one code file, types under `types/`.

Where a pattern repeats (one file per command, one per check, one per preset), the pattern is stated once and the full list follows it. The tree is then complete without listing the same shape forty times.

### `src/commands/`

Fourteen files, one per command, each under sixty lines: `init.ts`, `check.ts`, `apply.ts`,
`ignore.ts`, `add.ts`, `remove.ts`, `allow.ts`, `set.ts`, `declare.ts`, `why.ts`, `explain.ts`,
`doctor.ts`, `upgrade.ts`, `uninstall.ts`. Two more files sit beside them. `emit.ts` is the one function that prints a result as text or JSON and turns the errors gspot raises into exit 2. `flags.ts` holds the readers for the flag values commander hands over (`textFlag`, `listFlag`, `directoryOf`).

Completion registers
itself from `output/completion.ts` in `program.ts`, so it has no command file. A command file
registers its flags with commander, calls one function from another folder, and hands the result
to `emit`. No logic lives here.

### `config/`

Literal tables only: no function, no control flow, no import of anything but types.
`integrity/config-purity` guards the folder in the gate of this repository through the `config` role in its `gspot.toml`. A value lives here when a reviewer is expected to tune it or a message prints it; an
algorithm's own constant stays where it is used (D-22).

- `install-hints.ts`: mise, Homebrew, apt, winget, scoop per platform.
- `assets.ts`: where the gspot data lives: the repository from source, the embedded files in the binary; `build.ts` writes the index.

### `types/`

`config.ts`, `manifest.ts`, `finding.ts`, `record.ts`, `repository.ts`, `emit.ts`,
`naming.ts`, `structure.ts`, `doctor.ts`. Type aliases only; no runtime export.

A `*.fragment.*` template contributes a section to a file another preset owns (the ESLint flat
config, `ruff.toml`, `pyproject.toml`, `v8r.yml`); `emit/targets.ts` concatenates fragments in
selection order. Every check in every manifest carries `summary`, `why` and `fix`. Files under
`presets/` are data: the config-files preset claims them and the structure rules for code do
not apply.

## What is not in the tree

- No `scripts/` folder: build steps are `build.ts` in each package and `docs/generate.ts`;
  release steps are the workflow.
- No `src/index.ts` or barrel anywhere; `plugin.ts` is the ESLint plugin's entry because ESLint
  needs an object, and `main.ts` is the binary's.
- No `examples/`: the planted repositories are the examples and the docs link to them.
- No per-preset `docs/` folder: the corpus is one tree under `rules/` and manifests name files
  in it by path.
